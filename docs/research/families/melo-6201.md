# MELO P1 (family 6201) and MELO P1 TWS earphones: protocol research

Status: desk research only, without hardware. Nothing on this page has been confirmed against a live MELO P1.
It prepares support for a product family that the official HollyAudio app supports but we cannot test.

Sources and citation conventions (the same as `docs/PROTOCOL.md`):

- **A:** Android HollyAudio 3.1.0 (`com.hollyland.larkc1`), decompiled with jadx. Paths are relative to
  `jadx-out/sources/com/hollyland/`. The decompile used for this page is

  from `~/Downloads/HollyAudio_3.1.0_APKPure.xapk`).
- **I:** iOS HollyAudio 3.1.0 (`/Applications/larkSound.app/Wrapper/larkSound.app/larkSound`, arm64). These cite a

- **R:** Android resources. `values/strings.xml` comes from the base APK. Chinese strings come from `config.zh.apk`
  (`values-zh-rCN`).

## 0. TL;DR

| Topic | Answer |
|---|---|
| What it is | **MELO P1**: a "smart audio mixer" (China: 声卡, sound card) for singing and live streaming. Parts: an RX/mixer (the "main" RX plus an optional "sub" RX for a second phone), two wireless mics (TX), a charging case (BOX), a remote control (RC), and **MELO P1 TWS Monitor Earphones**. It also has a 3.5 mm instrument/monitor jack and a Bluetooth backing-track input. |
| Product IDs (`Product.java`) | RX main **1032 (0x0408)**, RX sub **1033 (0x0409)**, TX **1034 (0x040A)**, "DY" TX **1040 (0x0410)**, BOX **1035 (0x040B)**. Earphone **772 (0x0304)** is a synthetic app-side ID used for BLE/SPP, not a USB PID. USB VID is assumed to be 0x3547 **[?]**. |
| Transports | RX: **USB HID (interrupt endpoints, no report-ID layer)** *and* **BLE GATT** (service `FFE0`, write `FFE1`, notify `FFE2`). TX and BOX: USB only, and the app uses them only for firmware updates. Earphones: classic Bluetooth **SPP** on Android (RFCOMM UUID `0000E003-…`), with a separate Actions-style OTA TLV protocol. |
| Framing | The **"standard Moma" TLV frame**: `AA DD 06 <target> <control> <count BE16> { <cmd BE16> <type> <len BE16> <payload> }* [XOR]`. Replies start `BB DD`. **Command IDs are 16-bit.** Payload fields are **little-endian** (the header is big-endian). Frames are variable-length, unpadded, and can exceed 64 B. **This is not the legacy `AA DD cmd dst len` framing**: only the magic bytes are shared. |
| Checksum | Android: control `0x04`, plus 1 XOR byte over every preceding byte. iOS: control `0x00` with **no** checksum. The firmware therefore follows the control byte's checksum bits **[I]**. Neither app verifies reply checksums. |
| Session | No handshake or authentication. On connect, read device info `0x600A` (payload: device type), then poll heartbeat `0x600B` **every 3 s**. The 31-byte heartbeat carries batteries, link state, ear and RC state, and mic types. Live VU meters are **pushed** after subscribing with `0x6048` (100 ms interval). |
| Firmware gates | RX master firmware **≥ 4.0.0.1** switches the preset, level and switch-chain payloads to "V2" structures and opens home V3. **≥ 3.0.7.9** enables per-mic gain (`0x1319`). |
| Browser path | **Web Bluetooth is the best path.** It works fully on macOS, Windows, ChromeOS and Android Chrome, and avoids the HID reply problem. WebHID needs the device's HID descriptor, which is unknown. If replies use an undeclared report ID 0xBB (as on the A2), macOS drops them again. |
| Reuse | Very little of `codec.ts`, `commands.ts` or the heartbeat parsers carries over. The 6201 needs a new codec, a new command module, and a BLE transport. The `Transport` interface, the queue/timeout ideas in `device.ts`, the product registry and the UI scaffolding can be reused. Effort: medium to large. Confidence: high for the codec, medium for the payloads, low for the USB HID mapping. |

### 1.2 How the apps tell the parts apart

- **Android USB:** by USB PID, via `HlDevice.setProductId(device.getProductId())` (as for the A2). TX and BOX PIDs
  open the firmware-update flow. 1032/1033 open the home screen once device info has delivered the master firmware
  version (`C6201ServiceImpl.dispatchHome` waits up to `WAIT_FIRMWARE_VERSION_TIMEOUT_MS = 3000`). **[V]**
- **Android BLE (RX):** advertising, parsed by A `mic_ble/parser/ScanRecordParser.parse` and `DeviceParseV2`:
  - AD 1 must be `02 01 02` (flags, LE General Discoverable).
  - AD 2 must be type `0x09` (Complete Local Name), giving the device name.
  - AD 3 must be type `0x16` (Service Data, 16-bit UUID) and start with `BB BB` (UUID **0xBBBB**). Then come
    `productLine` (u8), `deviceId` (u8), an optional 11-byte ASCII SN, and an optional `"ssid:password"` string.
  - `ProductDeviceID.fromBytes(productLine = 4 (SOUND), deviceId)` resolves `C6201_INLAND` (deviceId 1, China) or
    `C6201_OVERSEA` (2) to product 1032, and `C6201_EAR` (3) to 772 (A `ble/core/model/ProductDeviceID.SOUND`). **[V]**
  - A Web Bluetooth filter that matches the RX only: two filters,
    `{ serviceData: [{ service: 0xBBBB, dataPrefix: new Uint8Array([4, 1]) }] }` and the same with `[4, 2]`, plus
    `optionalServices: [0xFFE0]`. The earlier one-byte prefix `[4]` also matched the **MELO P1 TWS earphones**
    (productLine 4, deviceId 3), which would be offered as a receiver and then fail at `FFE0` discovery (corrected
    2026-11-05, Phase 0/1 review). iOS tells them apart the same way: `-[HLConnectController didDiscoverPeripheral:advertisementData:]`
    @0x1001d2894 reads service data key `"BBBB"` (@0x1001d29d4) and tests the hex string's prefix: `"0804"` → type 17
    (OWS, @0x1001d2a00), `"0403"` → type 12 (earphones, @0x1001d2a54), `"0401"` → type 11 (MELO P1, @0x1001d2a84);
    `-[HLScanViewController didDiscoverPeripheral:advertisementData:]` @0x1001e5b44–0x1001e5b64 repeats the `"0401"` check.
    iOS accepts only `04 01`; `04 02` (C6201_OVERSEA) comes from Android. A `namePrefix` filter is a fallback, but the
    advertised name is unknown. **[V]** (prefixes) / **[I]** (that the RX advertises nothing else)
  - The user must turn BLE on at the RX: "Put the Mic and RX in the box, and long press the volume knob on the RX
    to turn the Bluetooth function on" (R `one_text`). **[V]**
- **Android earphones:** classic Bluetooth. `blemic/earphone/manager/EPConnectManager.getEPDeviceType` returns
  `EAR_6201` when the name contains `"TWS Monitor Earphone"` (or equals `product_ows_ear_6201`) **and** the MAC starts
  with `50:C0:F0`. OWS 6701 earphones share that MAC prefix. **[V]**
- **iOS:** the EA (iAP2) `modelNumber` `melo p1` gives type 11 → `HLSoundMainViewController`, and `melo p1 04`
  gives type 13 → `HLSingleUpgradeVC` (mic, upgrade only). Type 12 is the earphone card. See
  `docs/research/ios-protocol.md` §1.1. The iOS write chunk for types 11/13 is 500 bytes instead of 64. **[V]**
- **Firmware versions:** `0x600A` device info, per device type (§5.2).
  `larkc1/c6201/data/runtime/DeviceRuntimeManager.checkAllOnlineDeviceVersions` requests it for every unit that the
  heartbeat reports online. **[V]**

## 2. Transport

### 2.1 USB (RX, TX, BOX): HID interface, interrupt pipe, no report-ID layer

- **Interface and endpoints.** A `usb/core/HlUsbManagerImpl.findSuitableInterface` picks the first interface with
  `bInterfaceClass == 3` (HID) that has an interrupt IN and/or interrupt OUT endpoint. This is the same code path the
  A2 uses. **[V]** The endpoint addresses and `wMaxPacketSize` are unknown. **[?]**
- **Provider USB config** (A `protocol/core/sound/provider/Protocol6201Provider.providerUsbConfig`):
  `UsbCommandInfo(maxPacketSize = null, BULK, controlTransSize 64, needResponse true, reportId 773, ctlRead 1,
  ctlWrite 9, skipQueueDistinct false, overrides…)`. The transfer type is BULK, meaning `bulkTransfer()` on the
  interrupt endpoints. The report ID 773 and the control-request values apply only to the CONTROL path, so they are
  unused here. **[V]**
  - `maxPacketSize = null`: each request is split into chunks of the OUT endpoint's `getMaxPacketSize()`
    (`HlUsbManagerImpl.executeBulkTransfer`, `UsbPacketManager.splitData`). Chunks are **not padded** and continuation
    chunks carry **no header**: the frame bytes are simply cut. **[V]**
  - Override `CMD_APP_FIRMWARE_TRAN_PACKAGE`: `maxPacketSize = 512`. The OTA data frames are cut into 512-byte
    transfers, which hints that the OUT endpoint accepts 512-byte transfers. A high-speed interrupt endpoint is
    possible. **[I]**
  - Override `CMD_APP_DEVICE_INFO_GET`: `skipQueueDistinct = true`. The queue does not de-duplicate it, because it is
    sent once per device type. **[V]**
- **No report ID.** `Protocol6201Provider.createCommandPostBuilder()` never calls `setReportId`, so `0xAA` is byte 0 of
  every transfer, exactly as on the A2. The A2's HID stack therefore sees "report 0xAA out" and "report 0xBB in". **[V]**
- **Receive.** The read loop does `bulkTransfer(IN, maxPacketSize, 500 ms)` (`HlUsbManagerImpl.startDataReceiveLoop`).
  Chunks are concatenated in `DefaultPacketProcessor.processReceivedData` until
  `Protocol6201Provider.checkDataComplete` (`CommandStanderParser.parse(...) == SUCCESS`) says the frame is complete.
  There is no resync on garbage. **[V]**
- **Timeouts.** `CommandExecutionConfig(timeout 200 ms, timeoutRead 200 ms, retryCount 3)` (defaults, A
  `protocol/core/parser/CommandExecutionConfig`). Retries are stored but not used on the USB path, as for the A2. If
  5 bulk failures occur within 15 s, the app force-reconnects, with a 30 s cooldown (`C6201ServiceImpl.BULK_FAILURE_*`).
  **[V]**
- **USB audio.** The RX is also a UAC device. Upload/download stream switches, bit depth and channel layout are
  configured with `0x1306`, `0x1304` and, on iOS, `0x131B` (§5). **[V]**

## 3. Framing ("standard Moma" TLV)

### 3.1 Request (app → device)

Built by A `protocol/core/sound/transfer/CommandPostBuilder.build()`, configured by
`Protocol6201Provider.createCommandPostBuilder()` (`setSlaveIdentify(...)`, `setEnableStartFrame(false)`,
`setEnableEndFrame(false)`, `verificationAlgorithm(XOR)`, no report ID). iOS builds the same layout in
`+[HLCommandFrameBuilder frameWithSource:target:control:commands:startMagic:includeStart:endMagic:includeEnd:checksum:]`
@0x1000a3058. **[V]**

| Offset | Size | Field | Value |
|---|---|---|---|
| 0 | 2 | head | `AA DD` (`ProtocolHeader.HEAD_DOWN`) |
| 2 | 1 | source | `06` = `IDENTIFIER_PHONE_APP` (always) |
| 3 | 1 | target ("slave identify") | USB: `00` (`IDENTIFIER_BROADCAST`, the provider's default `ResolveConfig`). BLE: `01` (`IDENTIFIER_PHONE_RX`). iOS sends `01` on both. The enum (`DeviceIdentify`) is 0 broadcast, 1 phone RX, 2 camera RX, 3 TX1, 4 TX2, 5 BOX, 6 phone app, 255 default. |
| 4 | 1 | control | bit0 = start frame present; bit1 = end frame present; bits2–3 = checksum algorithm (0 none, 1 XOR, 2 CRC16, 3 CRC32); bit4 = long-package "reliable" mode. Android sends **`0x04`** (XOR). iOS `requestCommand:payload:` sends **`0x00`** (no checksum). The iOS start/end builder (`requestCommand:payload:needStartEnd:deviceType:`, control 7) is **not** a MELO P1 path: its only caller is `-[HLBleViewModel bleStartOTA]` (call @0x10015c9b8, MAX 2 BOX firmware update). |
| 5 | 2 | count, **big-endian** | number of command elements, + 1 if a start frame is present, + 1 if an end frame is present |
| 7 | 5 | start frame (optional) | `5A FA 00 00 00` (= cmd `0x5AFA`, type 0, len 0) |
| … | 5 + n | command element ×count | `cmd` (2, BE) · `type` (1) · `len` (2, BE) · `payload` (n) |
| … | 5 | end frame (optional) | `5E FE 00 00 00` |
| last | 1 | checksum (if bits2–3 ≠ 0) | XOR of **every** preceding byte from `AA` onwards (`ChecksumUtils.crcCalculate`). The CRC16/CRC32 options append only the low byte, an app bug, but the 6201 never uses them. |

- **Element `type`** (`ProtocolCmdType`): 0 NOTIFY, **1 REQUEST** (every app request, GET or SET), 2 RESPONSE_EXEC_RESP,
  3 RESPONSE_REQUEST_DATA. The cmd is given as a hex string (`"0x600B"`) and converted with
  `HexUtils.hexStringToByteArray`, which yields 2 bytes, big-endian. **[V]**
- **Length rule:** `len` covers the payload only. The whole frame is
  7 + Σ(5 + nᵢ) [+ 5 per start/end frame] [+ 1 checksum] bytes. There is **no padding** and no maximum other than
  u16. The transport splits frames (§2.1, §2.2). **[V]**
- **Batching:** one frame may carry several elements (`buildBatchRequest`, `MicUsbManager.buildBatchSendData`, iOS
  `requestCommandArr:…`). A reply with more than one element is decoded per element (`parseBatchResponse`). **[V]**
- **Payload byte order:** the frame header uses BE16, but **every payload entity is serialized little-endian**
  (`ByteBuffer.order(LITTLE_ENDIAN)` in all `*Serializer`/`*ExtKt` classes under `protocol/core/sound/data`). Ints are
  int32 LE, floats are IEEE-754 LE, and booleans are one byte, `1` = true. **[V]**
- **No sequence numbers.** Correlation is by cmd ID. The app queue de-duplicates identical pending commands unless
  `skipQueueDistinct` is set. **[V]**

### 3.2 Reply (device → app)

Parsed by A `protocol/core/sound/transfer/CommandStanderParser.parse` and iOS
`-[HL6201ViewModel receiveDataDeal]` @0x10026ea4c → `seprateDataWithCmdNum` @0x10026ec58. **[V]**

| Offset | Field | Parser behaviour |
|---|---|---|
| 0–1 | `BB DD` (`HEAD_UP`). `AA DD` is also accepted. | Android rejects anything else (FAIL). iOS compares the first 2 bytes and needs ≥ 7 bytes. |
| 2 | host/source identify | stored, not used for routing |
| 3 | slave/target identify | stored, not used |
| 4 | control | start/end flags, checksum bits, long-package bit (see the quirk below) |
| 5–6 | element count, BE | Android subtracts start/end frames. iOS stores it as `totalCmdNum` and subtracts 2 when control == 7. |
| 7… | elements `cmd(2,BE) type(1) len(2,BE) payload` | Each element is decoded by the executor registered for `cmd` (`Protocol6201ProviderProxy.getSupportedCommands`). |
| last | checksum | **Never verified** by either app. Android only checks that enough bytes are present. |

- **Parser quirk [V]:** `CommandStanderParser` reads the checksum field as the string `bit2 + bit3` and maps `"01"`
  → XOR, `"10"` → CRC16, `"11"` → CRC32. That is the reverse of the builder, where XOR is `1 << 2`. A reply with
  control `0x04` is therefore treated as "CRC16, needs 2 trailing bytes". This changes only the completeness check:
  zero padding on USB hides it, and on BLE it could make the app wait for one more byte. An independent
  implementation should use the builder's definition (bits2–3 as a little-endian 2-bit value), accept either reading
  when checking completeness, and not depend on the checksum.
- **Set acknowledgements:** almost every SET executor decodes `payload[0] == 0` as success (`DeviceControlConstant.SetResult`:
  0 SUCCESS, 1 FAIL). iOS `showConfigSuccess:cmd:` does the same (`seprateDataWithCmdNum`, `cbz` on the first payload
  byte). **[V]**
- **GET replies** carry the entity as the payload. What `type` the device puts in replies (2/3, or echoing 1) is
  **[?]**; neither app looks at it.

### 3.3 Differences from the legacy `AA DD` framing in `codec.ts`

| Aspect | Legacy (6118/6301/6302) | 6201 |
|---|---|---|
| Byte 2 | 8-bit command | `06` source |
| Byte 3 | destination `0x40 \| target` | target identify (`00`/`01`) |
| Byte 4 | length hi | control flags |
| Bytes 5–6 | length lo / payload | element count (BE16) |
| Command | 8-bit, one per packet | **16-bit**, inside TLV elements, several per frame |
| Length | ≤ 58, BE16 | u16 per element; the frame is unbounded |
| Packet | always 64 B, zero-padded | exact length, split into endpoint-size chunks or MTU-3 |
| Checksum | none (the iOS XOR is optional and ignored) | XOR over the whole frame when control bits2–3 = 1 (Android). None when 0 (iOS). |
| Payload endianness | mostly single bytes | little-endian int32/float structs |
| Reply source | `0x80`–`0x82` | identify byte (`01` RX, …) **[?]** |
| Push data | none (polled only) | VU frames are pushed after `0x6048` |

`+[NSData requestCommand:payload:]` @0x10011d7e0 → `requestCommandArr:payloadArr:controlType:0 deviceType:1`

(@0x10011d320: control = needStartEnd ? 7 : 4, target from `hl_targetByteForDeviceType:`, checksum always on) has a
single call site, `-[HLBleViewModel bleStartOTA]` @0x10015c9b8 (MAX 2 BOX OTA), where a non-BOX target resolves to 0.
So target 0 in frame 11 is what that path produces; there is no target discrepancy.

### 3.5 Fragmentation and reassembly (what an implementation must do)

1. **Send:** build the full frame, then split it into transport chunks: the HID OUT report size (USB) or ≤ MTU-3 /
   512 B (BLE). Do not repeat headers, and do not pad except to satisfy a fixed HID report size. Trailing zeros after
   a complete frame should be harmless, because the frame is self-delimiting through count + lengths. **[I]**
2. **Receive:** append chunks to a buffer. Once 7 bytes are present, walk the elements by `len`. The frame is
   complete when all `count` elements (and the optional end frame and checksum) are present. Discard any trailing
   padding. Resync by scanning for `BB DD` (the Android app does not resync; this is a library extension, like
   `FrameAssembler('stream')`).

## 4. Session

### 4.1 Connect

1. Open USB HID or BLE (enable `FFE2` notifications). There is no handshake or authentication. **[V]**
2. `0x600A` device info with payload `00` (sound card master). The firmware version gates the UI and payload
   structures (`Protocol6201SessionState.onDeviceInfoDecoded` stores `masterSwVersion`).
   `DeviceRuntimeManager.requestMasterDeviceVersionNow`. **[V]**
3. Start the heartbeat loop: `DeviceRuntimeManager.startHeartBeat` → `EventLooper` default period
   **3000 ms** (`application/common/util/EventLooper`, `this((i & 1) != 0 ? 3000L : j, …)`) → `getHeartInfo()` =
   `0x600B`, no payload. The device-list page (`larkc1/viewmodel/MainViewModel.heartLooper`) also polls every 3 s.
   iOS uses `-[HL6201ViewModel sendHeartInfo]` @0x10026e1f0 with a timer (interval not decoded **[?]**). **[V]**
4. For each unit the heartbeat reports online, send `0x600A` with that unit's DeviceType
   (`DeviceRuntimeManager.updateDeviceOnlineStatus` → `checkAllOnlineDeviceVersions`, de-bounced to 1 s). **[V]**
5. The home screen then reads its state: levels `0x1129`, music style `0x1139`/`0x1133`/`0x1135`, stream in/out
   `0x130B`/`0x1309`, monitor `0x112B`, and so on. iOS `+[HL6201Messenger getAllDevInfo]` @0x10023bb68 sends `0x1303`,
   `0x1137` and `0x1133`, then more after a delay. `getDeviceSetInfo` @0x10023c224 sends `0x1143`, `0x1301` and
   `0x1305`. `getRemoteInfo` @0x10023c0a8 sends `0x113F`, `0x1315` and `0x6044`. **[V]**

### 4.4 Notifications (device push)

- `0x6048` **HL_APP_CMD_NOTIFY_START**, payload `u8 count`, then `count × { u16 LE cmd, u16 LE intervalMs }` (default
  interval **100**, `HlSoundNotifyInfo.NotifyCmdInfo`). After this the device pushes the listed GET command's reply
  periodically. The app uses it for VU meters: `0x11EB` (all inputs and outputs) on the home/volume page, the guide and
  `C6201VuSubscriptionCoordinator`, and `0x11E2`, `0x11E5`, `0x11E6` and `0x11E8` on the Pro-Tuning pages
  (`HLProfessional*ViewModel`). **[V]**
- `0x6049` **HL_APP_CMD_NOTIFY_STOP**, empty payload, stops all pushes. **[V]**
- `0x113D` current-music-style notify is decoded as `int32 currentMusicStyleKey`. It is sent when the remote changes
  the preset **[I]**.
- The ear, RC and mic online changes are seen only through the heartbeat. **[V]**

### 4.5 Timeouts

- USB/BLE write and read timeouts are 200 ms (provider default). There is no request/response pairing at the
  transport level, so commands are fire-and-forget with the reply routed by cmd ID. **[V]**
- `DeviceRuntimeManager.deviceVersionRetryCount` retries the device-info read per device type. **[V]**
- For a browser library: one request in flight per cmd ID, a 500 ms reply timeout (BLE writes with response add
  latency), and heartbeat failure after about 3 missed beats → offline. **[I]**

### 5.8 Firmware update (OTA): **destructive**, document only

- Commands: `0x4006` notify OTA list (`isRxOta, isRxSlaveOta, isRxControlOta, u8 txOtaState, u8 earOtaState,
  isMicOta`); `0x4005` appoint device (`u8 devType, u8 devObj, i32 fwSize, i32 fwCrc`), reply `u8`; `0x4000` start
  (`i32 firmwareSize, i32 packageSize, i32 firmwareCrc`); `0x4003` data packets (raw chunk, 512-byte USB transfers),
  reply `{u8 ok (0 = ok), i32 pkgSeq}`; `0x4002` relocation (resend from seq); `0x4004` end; `0x4007` finish; `0x4008`
  check box state; `0x4001` suspend (no executor).
- Order: RC → MIC → EP → TX → sound card slave → master (A `c6201/data/firmware/OtaInfoEnum.DeviceOtaOrder`). USB
  main port only.
- iOS: `HL6201UpgradeTools` (`sendUpgradeStartCommand`, `sendNextDataPacket`, `retryCurrentPacket`,
  `sendUpgradeEndCommand`).
- **Do not implement without hardware and a recovery plan.**

## 8. Earphones (772) in detail, and other products

### 8.1 MELO P1 TWS Monitor Earphones

- Identity is covered in §1.1 and §1.2. The RX reports them in the heartbeat (bytes 22–26) and in `0x600A` with
  type 3 (EP1, left) / 4 (EP2, right). In `DeviceRuntimeManager.updateDeviceOnlineStatus`, `LEFT_CONNECT` clears EP2
  and `RIGHT_CONNECT` clears EP1, and `isEarLowBattery(LEFT_CONNECT)` reads `isEP1LowBat`. **[I]**
- Direct link (Android): SPP RFCOMM `0000E003-…`.
- Protocol: an Actions-style OTA TLV protocol (A `blemic/earphone/manager/OTAManager`), not the Moma frame:
  `cmd = [u8 serviceId][u8 commandId][0x80][u16 LE len]{ subTLV: [u8 type][u16 LE len][value] }*`.
  - Example: `requestRemoteParameters` = `09 02 80 00 00`.
  - `checkRemoteStatus` = service 9, cmd 1, with TLVs 1 fwVersion, 2 `00 00`, 3 VRAM, 4 mode, 9 `01`.
  - `notifyRemoteAppReady` = 9/9.
  - Handshake timeout 2 s, frame size 256, replies `0x0901`–`0x097D`.
  - `parseDeviceInfo` returns a 22-byte left device info block. **[V]**
- Features: battery and charging per bud, firmware version, OTA. Everything else (volume, mute, pairing,
  monitoring) goes through the RX (`0x130E`, `0x0022`, `0x112A`).
- Browser: Web Serial RFCOMM (desktop Chrome), or Web Bluetooth if the `E49A25F8` GATT service exists **[?]**.
  Low priority.

## 9. Reuse assessment

| Library part | Reuse for 6201 | Notes |
|---|---|---|
| `transport.ts` `Transport` / `BaseTransport` | **Yes, with changes.** | `send()` currently assumes one 64-byte packet. It needs a "frame" mode: send an arbitrary-length frame and let the transport chunk it. `onPacket` should deliver raw chunks to a per-family assembler. |
| `webhid.ts` | **Partly.** | The `raw` mapping (`sendReport(0xAA, …)`) matches the first chunk exactly. Continuation chunks and the report size are unknown until the descriptor is captured. Add the VID/PID filters for 1032–1040. Treat `capabilities.receive` as `'unknown'`. |
| `bridge.ts` (hidapi) | **Yes** for raw writes and reads | hidapi passes byte 0 as the report ID, the same as the A2. Linux works best. |
| New `webbluetooth.ts` | **New** | `requestDevice` with service data `0xBBBB` and `optionalServices: [0xFFE0]`; write FFE1 with response; notify FFE2; chunk ≤ 512. Works on macOS. **This is the recommended first target.** |
| `codec.ts` (`encodeRequest`, `decodeFrame`, `FrameAssembler`) | **No** (keep `xorChecksum`, `toHex`, `fromHex`) | New `codecMoma.ts`: `encodeMomaFrame({ target, control, elements[] })`, a streaming `MomaAssembler` (§3.5), and lenient checksum handling (§3.2 quirk). The 6303 group needs the same codec with report ID 8 and no checksum, so share it. |
| `commands.ts` (`Requests`, enums, heartbeat parsers) | **No** | New `commands6201.ts`: 16-bit IDs, LE struct helpers (u8/i32/f32 readers and writers), the heartbeat (31 B), device info (20 B), and setters from §5.3. Start with the "More Settings" set (about 20 commands, simple payloads). Add DSP and presets later. |
| `device.ts` (`HollylandDevice`) | **Concepts only** | The queue, timeouts, blind-write policy, destructive opt-in, traffic log, heartbeat loop and feature gates can be ported. Needed: correlation by 16-bit cmd, multi-element replies, pushed VU frames, per-unit online state, and firmware gates (3.0.7.9, 4.0.0.1). |
| `models.ts` | **Yes** (data) | Add the 6201 products: `family: '6201'`, 1032/1033 RX (USB+BLE), 1034/1040 TX and 1035 BOX (USB, upgrade-only, mark unsupported), and BLE identity (productLine 4, deviceId 1/2/3). The `Capabilities` shape does not fit; add a 6201 capability record. |
| `mock.ts` | **Pattern** | Build a 6201 mock that answers `0x600B`/`0x600A`/the settings commands, so the UI can be built without hardware. |
| UI | Partly | Battery and status cards and settings rows can be reused. The mixer, VU and preset UI is new. |

**Effort and confidence (without hardware):**

| Step | Effort | Confidence |
|---|---|---|
| Moma codec + assembler (+ unit tests from §3.4) | S (1–2 days) | **High.** Two independent builders (Android, iOS) agree. |
| Web Bluetooth transport for the RX | S–M | **Medium-high.** The UUIDs are confirmed in both apps. The advertising filter and long-write behaviour are unverified. |
| Heartbeat, device info, More Settings commands | M | **Medium-high.** Simple LE structs; per-field semantics partly inferred. |
| VU push (`0x6048`/`0x11EB`) | S | Medium |
| DSP effects (EQ, compressor, reverb …) | M–L | Medium. The structs are exact; the units and ranges need the UI code (`ui/professional/*`) per effect. |
| Presets / music styles (V1 + V2 blobs) | L | Low-medium. Large nested entities, tied to cloud JSON. |
| WebHID wired path | S to code, unknown to make work | **Low** until the HID descriptor and report size are captured (macOS reply delivery especially). |
| OTA, unpair, factory reset, SN write | – | Do not implement. |

## 10. Open questions and first live tests

1. **HID descriptor** of the RX (1032): collections, report IDs, report sizes, endpoint `wMaxPacketSize`. Run the
   existing probe CLI or `ioreg` dump, the same as the A2 capture (PROTOCOL.md §11.1). This decides whether macOS
   delivers `BB DD` replies, and whether frames over 64 B can be sent through WebHID.
2. **BLE**: the advertised name; whether service `FFE0` appears in `getPrimaryServices()`; whether notifications on
   `FFE2` carry whole frames or MTU-sized fragments; whether long writes (> MTU-3) are accepted; whether BLE needs to
   be switched on at the RX each time.
3. Reply header values: the source/target bytes, the element `type` (2/3?), and whether the device appends XOR when
   the request had control `0x00`.
4. Whether the device rejects a frame whose XOR is wrong (probe once, with a GET).
5. `micTypeRaw` value meanings, `rxGain*` semantics, `rxMicLock` values.
6. Whether TX (1034) and BOX (1035) answer `0x600B`/`0x600A` when connected directly over USB (the app only upgrades
   them).
7. Earphones: does the `E49A25F8` GATT service exist on the 6201 buds (Web Bluetooth path)?
