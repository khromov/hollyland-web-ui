# LARK MAX 2 (family 6701) and the OWS Monitor Earphone: protocol research

Scope: LARK MAX 2 mobile RX (USB PID 1026), camera RX (USB PID 1027), the charging case "BOX" (BLE, app id 101),
the Lark Max 2 TX (reached only through the RX or BOX), and the OWS Monitor Earphone (app id 102, "6701OWS").

Static analysis only. Nothing was sent to any device and no USB device was touched.

**Sources.**
- `A:` is Android HollyAudio 3.1.0, decompiled with jadx 1.5.6. The tree named in the brief (`scratchpad/jadx-out`) no longer existed, so the APK was decompiled again into
  `scratchpad/families-max2-6701/jadx-out/sources/`. Paths below are relative to `sources/com/hollyland/`.
  Resources are in `scratchpad/families-max2-6701/jadx-res/resources/res/` (`R:`). zh-CN strings come from `config.zh.apk` (`R-zh:`).
- `I:` is iOS HollyAudio 3.1.0 (`larkSound` arm64). Addresses are IMPs from `otool -ov`. Disassembly uses lldb, and `objc_msgSend` stubs
  were resolved through `__objc_selrefs` with `scratchpad/families-max2-6701/tools/stubs.py`.

**Markers.**
- **[V]**: read directly from code, and the two apps agree, or only one app has the path.
- **[I]**: inferred from code, but not stated explicitly.
- **[?]**: unknown, or needs hardware.

## 0. Key findings

1. **The USB RX does *not* speak the legacy `AA DD cmd dst lenHi lenLo` framing.** Both MAX 2 RX variants and the BOX
   speak the **"standard Moma" multi-item TLV framing**, the same frame family as 6201 (MELO P1) and 6303 (LARK M3) [V].
   The frame is
   `AA DD 06 <target> <control> <itemCountBE16> [5A FA 00 00 00] { cmdBE16 type lenBE16 payload }* [5E FE 00 00 00] <XOR>`.
   Commands are 16-bit (`0x600B` heartbeat, `0x6006` noise, …). Replies start `BB DD`
   (`A:blemic/operation/BleMicCmd.cmdSingleSend/cmdMultiSend`, `A:blemic/operation/BleMicCommUtil.parseNotifyResult`;
   `I:+[NSData requestCommand:payload:needStartEnd:deviceType:] @0x10011d320` →
   `+[HLCommandFrameBuilder frameWithSource:target:control:commands:startMagic:includeStart:endMagic:includeEnd:checksum:] @0x1000a3058`).
2. **USB and BLE use the same bytes.** Only the target byte changes. Over USB it is the RX's own id: 1 for the mobile RX, 2 for the camera RX. Over BLE it is
   the unit addressed through the BOX: 2 RX, 3 TX1, 5 BOX (`BleMicCmd.<init>`, `ServiceManager.bleService().isBle()` branches).
3. **Byte 0 is still `0xAA` out and `0xBB` in**, so the macOS report-ID problem of the A2 applies unchanged *if* the
   MAX 2 RX's HID descriptor uses report IDs. The descriptor is not in either app [?]. Frames are variable length (23 to 75 B)
   and are written unpadded. Some replies are longer than 64 B, which implies the RX's interrupt-IN reports are larger than 64 B [I] (§2.1).
4. **The BOX is a BLE GATT peripheral.** It uses service `0000fee7-0000-1000-8000-00805f9b34fb`, and one characteristic
   `0000fec1-…` carries both writes (without response) and notifications. The app requests an MTU of 512 and does no bonding
   (`A:blemic/operation/BleBoxOption`; `I:-[HLBluetoothManager isMessageChannelReady] @0x1002accf0`, `+[HL6701Messenger …]` writes to `@"FEC1"`).
   → **Web Bluetooth gives full send and receive** on Chrome for macOS, Windows, ChromeOS and Android. This is the easiest path to a fully working MAX 2 on macOS.
5. **Session.** Over USB the app polls heartbeat `0x600B` every **3 s**. The 49-byte payload carries battery, online state, every setting,
   timecode and OWS earphone state. Over BLE **Android** polls nothing: per-unit `0x600A` version/battery queries, a "get all" multi-item
   frame and device-pushed status items (`0x6000`–`0x6008`) are used instead. **iOS does poll over BLE**: `0x600B` to target 2 (RX)
   through the BOX every 3 s (§4.2; corrected 2026-11-05 in the Phase 0/1 review, this item used to say "over BLE nothing is polled").
6. **The OWS earphone is a different product with a different protocol.**
   - Android: Classic Bluetooth SPP, RFCOMM UUID `0000E003-…`.
   - iOS: BLE GATT on the Actions-Semi OTA service `E49A25F8-F69A-11E8-8EB2-F2801F1B9FD1`, plus info service `FFD0`/`FFD2`.
   - The direct connection only shows L/R battery, version and SN, and runs OTA.
   - Every user-facing OWS control (pair, monitor on/off, play/pause, volume) is a **MAX 2 RX command** (`0x6017`–`0x601A`).

**Browser path.** WebHID (desktop Chrome/Edge) or the existing root-libusb bridge.
- macOS: full duplex only if the replies' report ID is declared, or the descriptor has no report IDs [?]. Otherwise the RX is write-only, like the A2.
- Linux/ChromeOS (hidraw): the same as macOS. The kernel's HID core drops undeclared input report IDs before hidraw (PROTOCOL.md §11.9).
- WebUSB cannot claim HID.

**Required change.** The current `WebHidTransport.send` pads to and rejects anything over 64 B (`src/lib/protocol/webhid.ts`). MAX 2 frames must be padded to the
*declared* output-report length instead. The bridge's "exactly 64 bytes" contract (`src/lib/protocol/bridge.ts` line ~332) also needs a variable length.

**Hardware to-do.** Dump the HID report descriptor of a 0x0402/0x0403 (`ioreg -l -w0 -r -c IOHIDDevice` or WebHID `device.collections`) before deciding on the macOS behaviour.

## 3. Framing (shared by USB RX and BLE BOX)

### 3.1 Byte layout

Host → device (`A:blemic/operation/BleMicCmd.cmdSingleSend / cmdMultiSend / cmdMultiMapSend / cmdNoStartEndFrame`;
the generic builder is `A:protocol/core/sound/transfer/CommandPostBuilder.build`; I `+requestCommand:payload:needStartEnd:deviceType: @0x10011d320`):

| Offset | Size | Field | Value |
|---|---|---|---|
| 0–1 | 2 | magic | `AA DD` (`ProtocolHeader.HEAD_DOWN`). Replies use `BB DD` (`HEAD_UP`, `QueryDeviceResult.getMasterStationPrefix`) |
| 2 | 1 | source | `06` = phone app (`DeviceIdentify.IDENTIFIER_PHONE_APP`) |
| 3 | 1 | target | `DeviceIdentify`: 0 broadcast, **1 mobile RX**, **2 camera RX**, 3 TX1, 4 TX2, **5 BOX**, 6 app, 10 TX3, 11 TX4, 255 default |
| 4 | 1 | control | bit0 = start item present, bit1 = end item present, bits2–3 = check (0 none, **1 XOR**, 2 CRC16, 3 CRC32), bit4 = long-package mode (0 default, 1 reliable) (`CommandPostBuilder.build`, `VerificationAlgorithm`, `LongPackageSendMethod`). The app always sends **`07`** (start + end + XOR). The exception is USB OTA data, which uses `04` (XOR only) |
| 5–6 | 2 | item count, **BE16** | number of items **including** the start and end markers (`intToByte2(size + 2)`) |
| 7 | 5 | start item | `5A FA 00 00 00` (cmd 0x5AFA, type 0, len 0), only if bit0 is set |
| … | 5+n | command item ×N | `cmdHi cmdLo type lenHi lenLo payload[len]`. **Length is BE16** (`NumberUtil.intToByte2` is big-endian) |
| … | 5 | end item | `5E FE 00 00 00`, only if bit1 is set |
| last | 1 | checksum | **XOR of every preceding byte**, including `AA DD` (`BleMicCommUtil.crcCalculate`; iOS checksum type 1 = `getOrData:`) |

Item `type` (`ProtocolCmdType`): **0 notify** (device push), **1 request** (the app uses 1 for both get and set; a get carries an empty payload),
**2 exec response** (set ack: `payload[0]` 0 = success, 1 = failure, `DeviceConnectVariable.CmdSetResult`), **3 response with data** (get reply).

Receive side (`BleMicCommUtil.parseNotifyResult`):
- It accepts a frame only if it starts `BB DD`.
- It reads `control` from byte 4 (`byteToBits` index 7 = bit0) and `count` from bytes 5–6 (BE).
- `items = count − (start?1:0) − (end?1:0)`. The first item is at offset `12` if the start bit is set, else `7`.
- `count > 3` with markers (i.e. more than one command item) → composite reply (`MicCompositeInfo`). Otherwise the single item is matched by its 16-bit cmd.
- **Bytes 2–3 (src/tgt) are ignored, and the XOR is not verified** [V]. Payload offset = item start + 5.

Endianness inside payloads is mixed. Header fields are BE. OTA sizes, CRC32, OTA sequence numbers and Bat3c fields are **LE32/LE16**
(`NumberUtil.intToByte4` / `intToByte22` are little-endian). System time is **BE64** (`longToByte8`).

**Sequence numbers.** There are none. Replies are correlated by cmd ID and type. OTA data carries an LE32 sequence number in the payload (`BleFileUpload`, `PROTOCOL_PKT_SEND_SEQ_LENGTH = 4`).

### 3.2 Differences from the legacy framing (codec.ts)

| | Legacy (6118/6301/6302) | MAX 2 / Moma |
|---|---|---|
| Header | `AA DD cmd dst lenHi lenLo` (6 B) | `AA DD src tgt ctl cntHi cntLo` (7 B) |
| Command id | 8-bit in the header | 16-bit, per item |
| Items per frame | 1 | N (the app batches up to 8 gets in one frame) |
| Target | `0x40|unit`, reply `0x80|unit` | absolute ids 1,2,3,4,5,10,11. Reply src not parsed |
| Length | BE16, payload only, ≤58 | BE16 per item. Frame length is implicit |
| Padding | always 64 B | none. Exact length on USB and BLE |
| Checksum | none | XOR over the whole frame (control bits 2–3 = 1) |
| Markers | none | start `5A FA 00 00 00`, end `5E FE 00 00 00` |
| Ack | set reply has the same cmd, same layout | item type 2, `payload[0]` = result code |

### 3.4 Fragmentation
- Android USB: one IN transfer = one frame, no reassembly. Android BLE: MTU 512, so no reassembly.
- iOS: reassembles in `-[HLBleViewModel receiveDataDeal]`. It searches for `BB DD`, derives the header length from the control bits (7/9/11 thresholds) and the
  item count from bytes 5–6, then calls `seprateDataWithCmdNum:` [V for the existence of reassembly; details [I]].
- **Web:** implement a streaming assembler. Find `BB DD`, read `ctl` and `count`, walk the items using their BE16 lengths, add 1 byte
  of XOR when bits 2–3 are 01, then emit. Optionally verify the XOR and log mismatches.

## 4. Session

### 4.1 Connect sequence
- **USB.** There is no handshake.
  1. `HLBleDeviceActivity.onStart` sends `AddListener(USB)`.
  2. It then calls `getIsSupportFourMic()`, which reads version `0x600A [01]` (RX) to evaluate the 3.0.0.50 gate.
  3. That is followed by `GetMicQuantity 0x6016` (new firmware) or a "get all".
  4. The coroutine `HLBleDeviceActivity$getDeviceAllInfo$1` then sends, 200 ms apart:
     - `0x600A` for RX, BOX, TX1 and TX2 (and TX3/TX4 when relevant),
     - the "get all" multi-item frame,
     - `0x6009` system time,
     - and over USB, `GetTxIdentify 0x6013` (`HLBleDeviceActivity.getFourModeOrVersion`, `$getDeviceAllInfo$1.invokeSuspend`).
- **BLE.**
  1. Connect (FastBle) to 0xFEE7, set MTU 512, enable notify on FEC1.
  2. On `CONNECT_SUCCESS` the activity shows "Connected" and runs the same version / get-all / time sequence (`HLBleDeviceActivity$initObserver…emit`, `ConnectDeviceStatus` branch).
  3. "Disconnect" (BLE only) calls `unPairDevice(address)`, which deletes the stored entry and disconnects.

### 4.2 Heartbeat `0x600B` (USB; over BLE on iOS only)
- Sent every **3000 ms**, first after 1000 ms (`HLBleDeviceActivity$mRunnable$1.run`, `onPermissionGranted`). The settings,
  laboratory and wireless-monitor screens also poll every 3 s.
- Over BLE, Android's `BleDeviceControlViewModel.getHeartInfo()` **returns without sending**.
- **iOS polls it over BLE too [V]:** `-[HLBleDeviceController viewDidLoad]` (the controller created for the FEE7 BOX,
  deviceType 16) schedules `sendHeartInfo` on a repeating 3.0 s timer (@0x100243fa4–0x100243fc4: selector `sendHeartInfo`,
  `fmov d0, #3.0`, `mov w5, #1` → `scheduledTimerWithTimeInterval:target:selector:userInfo:repeats:`).
  `-[HLBleDeviceController sendHeartInfo]` @0x1002454ec sends `0x600B` with an empty payload through
  `requestCommand:payload:deviceType:` (`mov w2, 0x600b; mov x4, 0`, call @0x100245530), and
  `+[NSData hl_targetByteForDeviceType:]` @0x10011d288 turns deviceType 0 into target **2** (RX) when the connected
  entity's deviceType is `0x10` (BOX), else 0. So the BOX forwards a read-only heartbeat request to the RX, and a web
  client can poll the same way (registry row 101: `heartbeatIntervalMs: 3000`). Whether the reply comes back through the
  BOX intact is a hardware-check item.
- Reply: one item `60 0B 03 <len>` plus the payload below. Offsets are relative to the payload start (`BleMicCommUtil.generateHeartInfo`; field names from

### 4.3 Notifications (BLE)
`parseNotifyResult` accepts single-item frames for `0x6000` (BOX battery), `0x6001` (RX battery) and `0x6002` (TX online + battery for 2 mics)
without any request for them, and Android sends no heartbeat over BLE. So the BOX evidently **pushes** these status items [I]. Their item type is probably 0 (notify) [?].
iOS adds the 3 s `0x600B` poll to target 2 on top of the pushes (§4.2).

### 4.4 Timeouts
- USB write timeout 250 ms, read timeout 1000 ms (`USBHIDService` `CommandExecutionConfig`). There is no app-level retry for settings.
- OTA reply timeout: USB 8000 ms, BLE 3000 ms. Up to 3 tries (`BleFileUpload.USB_REPLY_TIME_OUT / BLE_REPLY_TIME_OUT / MAX_TRY`).
- Inter-command spacing on connect is 200 ms.

## 7. OWS earphone protocol (direct link; for completeness)

- **Info frame.**
  - SPP: the earphone pushes `A0 07` + 46 bytes. The app skips 2 and parses 44 (`A:blemic/earphone/manager/OTAManager$ProcessRunnable.run`, `parseDeviceInfo`).
  - BLE (iOS): characteristic FFD2 holds the same 44 bytes. Layout: `[0] L online, [1] L battery, [2..5] L version (4 bytes, printed reversed as a.b.c.d), [6..21] L SN (16 ASCII), [22] R online, [23] R battery, [24..27] R version, [28..43] R SN` (`I:-[HLBleOWSEntity initEntityWithData:] @0x1001fdd18` uses the same offsets) [V].
- **Enter OTA.** `A0 06` + 62 zero bytes (64 B) (`OTAManager.startOTA`). The earphone answers `A0 06` + 4 bytes.
- **OTA.**
  - Actions-style TLV: `[serviceId 0x09][commandId][0x80][lenLE16][subTLVs: type u8, lenLE16, value]` (`OTAManager.assembleCommand/assembleTLV`).
  - Commands: `09 01` check remote status (TLVs 1 fw version, 2 `00 00`, 3 VRAM 16 B, 4 mode, 9 `01`), `09 02` request parameters (`09 02 80 00 00`), `09 09` app ready (`09 09 80 04 00 01 01 00 <state>`), and device→app `09 03`/`09 05`/`09 07`/`09 7D` data requests.
  - Result TLV `0x7F` with int32 100000 = OK.
- All of this is **firmware update**, which is out of scope for the web UI. The OWS battery and connection state are already in the MAX 2 heartbeat (bytes 23–27, 48).

**Confidence.**
- Framing and checksum: **high**. The Android builder, the Android generic `CommandPostBuilder`, the iOS frame builder and the iOS heartbeat parser all agree.
- Command IDs and payloads: **high** for set payloads, **medium** for reply-side details such as the src/tgt bytes and the push item types.
- BLE GATT layout: **high** (both apps). Advertising filter: **medium**.
- USB HID report layout and macOS receive: **low** until a descriptor is seen.
- OWS: **low** (no useful features beyond what the RX heartbeat gives).
