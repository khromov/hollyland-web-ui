# LARK M3 (family 6303): protocol research for a browser port

Scope: the LARK M3 receivers (USB PIDs 1036–1039) and everything the official HollyAudio 3.1.0 app reaches through
them (TX1–TX4, secondary RXs, the camera-RX hot-shoe accessory, Bluetooth monitor earphones). Static analysis only;
no M3 hardware was available and no USB device was touched.

Citation conventions (same as `docs/PROTOCOL.md`):
- **A:** Android HollyAudio 3.1.0, jadx. Paths are relative to `jadx-out/sources/com/hollyland/` unless they start
  with `defpackage/` (relative to `jadx-out/sources/`). The tree used for this report was regenerated from
  `HollyAudio_3.1.0_APKPure.xapk` (base `com.hollyland.larkc1.apk`) into
  `scratchpad/families-m3-6303/jadx-out/` because the shared `scratchpad/jadx-out/` was missing.
- **I:** iOS HollyAudio 3.1.0 (`larkSound`, arm64), `@0x…` = virtual address. The HL6303 code is Swift; field and
  enum-case names come from `__swift5_fieldmd` (parsed with `scratchpad/families-m3-6303/tools/swiftfields.py`).
- **R:** Android `res/values/strings.xml`; **L10n:** iOS `en.lproj/Localizable.strings`.
- Confidence tags: **[V]** read directly in code, **[I]** inferred with strong support, **[?]** needs hardware.

## 0. TL;DR

* **Same physical channel as the A2, different framing.** The M3 RX is driven over its USB HID interrupt pipe exactly
  like the A2 (`HlUsbManagerImpl` BULK path on the interrupt endpoints), but every packet carries an explicit
  **HID report ID `0x08`** in byte 0, followed by the "standard Moma" multi-frame envelope
  `AA DD 06 <target> <flags> <frameCount BE16> { <cmd BE16> <type> <len BE16> <payload> }…`, **no checksum**,
  zero-padded to **64 bytes** (or **512** when longer). Commands are **16-bit** (`0x6000` heartbeat, `0x1003` noise…).
* **macOS should work in both directions [I].** The A2 is write-only on macOS because its replies use the undeclared
  report ID `0xBB`. The M3 replies as `08 BB DD …` and the app strips byte 0 as a report ID
  (`CommandStanderParser(8)`), so the replies use report ID 8, which a HID-conformant descriptor must declare.
  Descriptor not seen yet: **verify with a descriptor dump** (WebHID `device.collections` or ioreg).
* **Browser API: WebHID only.** No phone-facing BLE path exists for the M3 (the GATT UUIDs in the provider are dormant
  copy-paste from 6201), iOS uses iAP2 External Accessory (unusable from a browser), WebUSB cannot claim HID.
* **No handshake, polled.** Heartbeat `0x6000` every **1.5 s** on both apps (A `HLDeviceVolTrack6303Activity.getHeartTime() = 1500`,
  I `NSTimer timerWithTimeInterval:1.5` @0x1004b6378). 30-byte status reply. Extra loopers on the voice-profile
  page (`0x1F15` / 1.5 s, `0x1F19` / 2 s) and a Bluetooth status poll (`0x0039` / 5 s) in 2T2R mode.
* **Catalogue is complete and byte-exact.** 87 command classes with generated little-endian serializers
  (`*EntityExtKt.cmdSerialize` / `*EntitySerializer.deserialize`); the iOS `HL6303CommandType` raw-value table
  (@0x100c1a318) independently confirms every ID.
* **Voice profiles ("Bel") are device-side DSP.** `0x1F05` carries a 372-byte `ModAlgBelT` struct
  (compressor, de-esser, 10-stage biquad EQ **coefficients**, exciter). The repo's `src/lib/dsp` `CmsisEmulator`
  already computes the same `numStages` + `coeffs[5·n]` that the app sends, so voice profiles can be built and
  previewed in the browser bit-exactly.
* **AI translate is not a feature in 3.1.0**: `HL6303AiTranslateVc` has no fields and its sibling
  `HL6303AiTranslateVc11` is the `Test4ChanelRecordVc.swift` 4-channel recorder test page. No Android counterpart.

## 2. Transport

### 2.1 Android (the reference for a browser port)

* Same USB stack as the A2: `usb/core/HlUsbManagerImpl.findSuitableInterface` takes the first HID-class interface with
  interrupt endpoints and claims it; writes are `bulkTransfer(OUT, …)` on the **interrupt OUT** endpoint, reads are
  `bulkTransfer(IN, buf, IN.maxPacketSize, 500 ms)` in a loop (`HlUsbManagerImpl$startDataReceiveLoop`). **[V]**
* Provider USB config `protocol/core/sound/provider/Protocol6303Provider.getUsbConfig` →
  `UsbCommandInfo(null, BULK, …, mask 765)`: transfer type **BULK** (= raw interrupt pipe, no SET_REPORT),
  `maxPacketSize = null` (use the endpoint's wMaxPacketSize). Overrides: `CMD_APP_FIRMWARE_TRAN_PACKAGE` (0x4003) and
  `CMD_APP_HOTSHOP_FIRMWARE_TRAN_PACKAGE` (0x4012) use `maxPacketSize = 512`. Control transfers are never used. **[V]**
* `HlUsbManagerImpl.executeBulkTransfer` splits a packet at `maxPacketSize` (`UsbPacketManager.splitData`); every
  6303 packet is 64 or 512 bytes (§3.3). **[V]**
* Receive reassembly: `usb/core/packet/PacketProcessor6303.processReceivedData` returns `Complete(newData)` only if
  **that single IN chunk** parses as a complete frame (`Protocol6303Provider.checkDataComplete` →
  `CommandStanderParser.parse(...) == SUCCESS`); it never concatenates chunks. Replies up to 413 bytes exist
  (`0x1F18`), so the M3's IN endpoint must deliver ≥ 413 bytes per read, i.e. a **high-speed 512-byte interrupt
  endpoint** **[I]**. Firmware chunks are `usbService().singlePackDataSize() − 4` =
  `wMaxPacketSize − 13 − 4` bytes (`FirmwareUpgrade6303ViewModel` line ~2140), which yields exactly 512-byte packets
  when wMaxPacketSize = 512 **[I]**.
* Timing: `Protocol6303Provider.getCommandExecutionConfig()` = defaults **200 ms write / 200 ms read / retry 3**
  (`CommandExecutionConfig` default ctor); `mic_usb/messenger/UsbMessenger6303` queues commands through a coroutine
  channel and spaces sends by **~50 ms** (`UsbMessenger6303$1.invokeSuspend`, `DelayKt.delay(50)`); OTA calls bypass
  the queue (`manager.sendData` directly).
* Bluetooth: `Protocol6303Provider.getBluetoothConfig` declares service `0000ffe0-…`, write `0000ffe1-…`, notify
  `0000ffe2-…` and `mic_ble/MicBleServiceImpl` can create a `BleMessenger6303`, but **no BLE device type maps to
  6303**: `ble/core/model/ProductDeviceID` has no 6303 entry and `OpenPageHelper.obtainBleIntentByDeviceType` only
  routes 6701. `BaseCommViewModel.obtain6303Messenger` picks BLE only when a 6201/6701 BLE session set `isBle`.
  So there is **no phone→M3 BLE control channel** in this app. **[V]**

### 2.2 iOS

* External Accessory (iAP2) over USB, protocol `com.hollyland.protocol`; `HL6303MessageService` is an
  `EASessionDelegate` (`inputStreamReceive(_:)`, queue `com.hollyland.hl6303.sendQueue`, fields `minSendInterval`,
  `commandIdToTaskIds`, `timeoutTimers`). The iAP2 interface is not usable from a browser. Whether the iOS byte
  stream also carries the `0x08` prefix was not traced **[?]** (irrelevant for WebHID).

### 2.3 HID report IDs and browser fit

| Question | Answer |
|---|---|
| Report ID on OUT | **0x08** at byte 0 (`Protocol6303Provider.reportId = 8`, `createCommandPostBuilder().setReportId(8)`) **[V]** |
| Report ID on IN | **0x08**: the parser drops byte 0 before matching `BB DD` (`new CommandStanderParser(8)`, `parse`: `copyOfRange(data, 1, …)`) **[V]** |
| Declared in the descriptor? | Very likely (a firmware that tags its reports with ID 8 is following HID numbering, unlike the A2 whose first byte is the frame magic) **[I]**. Not seen. |
| OUT/IN report sizes | 63 data bytes for short frames, 511 for long frames (64/512 incl. ID). Whether the descriptor declares 63, 511 or both via two IDs is unknown **[?]** |
| Interrupt vs feature | Interrupt (BULK path). No GET/SET_REPORT. **[V]** |

* **WebHID mapping (proposed):** `device.sendReport(0x08, packet.subarray(1))` where `packet` is the 64/512-byte buffer
  the Android builder produces; on `inputreport` with `reportId === 0x08`, rebuild `[0x08, ...data]` and feed the
  6303 decoder (or decode `data` directly with the report ID already stripped).
* **macOS**: if ID 8 is declared for input, IOHIDFamily delivers the replies → full read/write in Chrome **[I]**.
  If the descriptor declares only a 63-byte input report, replies longer than 63 bytes (`0x1F04`, `0x1F18`,
  `0x0029`, PDL lists) may be truncated or dropped; everything in the home/settings pages fits in 64 bytes.
* **Windows**: Chromium requires the output buffer to match the declared report length; send exactly the declared size
  (pad to 63 or 511) **[?]**.
* **Linux/ChromeOS (hidraw)**: raw reports, expected to work.
* **Android Chrome / iOS Safari**: no WebHID; WebUSB cannot claim HID interfaces (and the iAP2 vendor interface needs
  Apple MFi authentication). No browser path on phones.
* **Chooser filters**: `{ vendorId: 0x3547, productId: 0x040C..0x040F }` plus a fallback with an empty filter list,
  because the M3 VID is unconfirmed.
* **Node bridge** (`scripts/bridge.ts`, hidapi): `write([0x08, ...frame])` works the same way; hidapi returns
  numbered reports with the ID byte first.

## 3. Framing ("standard Moma" envelope, 6303 profile)

### 3.1 Request layout

Built by `protocol/core/sound/transfer/CommandPostBuilder.build()` with the 6303 settings from
`Protocol6303Provider.createCommandPostBuilder()` (`setReportId(8)`, `setEnableStartFrame(false)`,
`setEnableEndFrame(false)`, `verificationAlgorithm(NONE)`) and `buildPacket(...)`, which overrides the target with
`ResolveConfig.identify` (default `IDENTIFIER_BROADCAST`; `MicUsbManager.buildSendData` passes `null` → default). **[V]**

| Offset | Size | Value | Notes |
|---|---|---|---|
| 0 | 1 | `0x08` | HID report ID |
| 1–2 | 2 | `AA DD` | `ProtocolHeader.HEAD_DOWN` (replies `BB DD` = `HEAD_UP`) |
| 3 | 1 | `0x06` | source = `DeviceIdentify.IDENTIFIER_PHONE_APP` (hard-coded in `build()`) |
| 4 | 1 | `0x00` | target = `IDENTIFIER_BROADCAST` for every Android USB command. Enum: 0 broadcast, 1 phone RX, 2 camera RX, 3 TX1, 4 TX2, 5 box, 6 app, 255 default |
| 5 | 1 | `0x00` | control flags: bit0 start-frame, bit1 end-frame, bits2–3 checksum (0 none, 1 XOR, 2 CRC16, 3 CRC32), bit4 long-package "reliable". 6303 = all zero |
| 6–7 | 2 | `00 01` | number of command frames, **big-endian** (+1 per start/end frame when enabled) |
| 8–9 | 2 | cmd | 16-bit command ID, **big-endian** (`HexUtils.hexStringToByteArray("0x6000")` → `60 00`) |
| 10 | 1 | `0x01` | `ProtocolCmdType`: 0 NOTIFY, 1 REQUEST, 2 RESPONSE_EXEC_RESP, 3 RESPONSE_REQUEST_DATA |
| 11–12 | 2 | len | payload length, **big-endian** |
| 13… | len | payload | **little-endian** fields (all generated serializers use `ByteOrder.LITTLE_ENDIAN`) |
| … | | `00…` | zero padding: `len < 64` → **64**, else `len < 512` → **512**, else as is (`Protocol6303Provider.buildPacket`; `len` includes the report ID, and both comparisons are strict, so a packet of exactly 64 bytes is padded to 512) |

* Fixed overhead = **13 bytes** (`cmdSingleStandardSize()` builds a frame for `0x0000` with no payload). So payloads
  ≤ 50 bytes give a 64-byte packet; 51–499 bytes give a 512-byte packet (a 51-byte payload makes a 64-byte packet,
  which `buildPacket` pads to 512 because it tests `< 64`); ≥ 500 bytes are sent unpadded. (Corrected 2026-11-05 in the
  Phase 0/1 review; earlier text said ≤ 51 bytes fit 64.)
* **No checksum, no sequence number, no escaping.** Several command frames may share one packet (frame count > 1,
  `buildBatchRequest`), but the 6303 messenger never batches; replies with > 1 frame are handled
  (`Protocol6303Provider.parseBatchResponse`).
* Optional start/end frames (`5A FA 00 00 00` / `5E FE 00 00 00`) exist in the envelope but are disabled for 6303
  (`ExtraInfo6303.isWithStartEndFrame` defaults to true but nothing reads `ExtraInfo6303`).
* Parser quirk: `CommandStanderParser.parse` reads the checksum bits in reversed order (bit2 then bit3), so a builder
  XOR flag would parse as CRC16; irrelevant here (flags are 0) and the parser never verifies a checksum anyway.

### 3.2 Reply layout

Same envelope with `BB DD`. `CommandStanderParser(8).parse`: strip byte 0 (report ID), require `BB DD` or `AA DD`,
read source (byte 3 of the packet), target (byte 4), flags, frame count, then frames until the count is exhausted;
`SUCCESS_NOT_ENOUGH` if a frame overruns the buffer. Dispatch is by the **command ID string**
(`IProtocolProvider.findCommandExecutor` → `isMatch` case-insensitive `"0x6000"`). Source/target/type bytes of
replies are **not checked** by the app; expected values are source 1/2 (phone/camera RX), target 6, type 2 or 3
**[?]**.

### 3.3 Example frames (bytes derived from the builder; checked by round-tripping through a Python model of
`CommandPostBuilder` + `CommandStanderParser`, `scratchpad/families-m3-6303/tools/frames.py`)

| Purpose | Packet (hex) |
|---|---|
| Heartbeat GET `0x6000` | `08 AA DD 06 00 00 00 01 60 00 01 00 00` + 51 × `00` (64 B) |
| NC on, Medium `0x1003` [dev 0, level 1, on 1] | `08 AA DD 06 00 00 00 01 10 03 01 00 03 00 01 01` + 48 × `00` |
| Channel mode Stereo `0x1005` [dev 0, mode 1] | `08 AA DD 06 00 00 00 01 10 05 01 00 02 00 01` + 49 × `00` |
| Phone-RX volume step 4 of 6 `0x100D` [dev 0, level 3] | `08 AA DD 06 00 00 00 01 10 0D 01 00 02 00 03` + 49 × `00` |
| Mute TX2 `0x1001` [tx 2, mute 1] | `08 AA DD 06 00 00 00 01 10 01 01 00 02 02 01` + 49 × `00` |
| Device info of RX1 `0x600A` [deviceId 6] | `08 AA DD 06 00 00 00 01 60 0A 01 00 01 06` + 50 × `00` |
| Firmware versions, 4T4R system `0x6012` [0] | `08 AA DD 06 00 00 00 01 60 12 01 00 01 00` + 50 × `00` |
| Template name "My Voice" for TX1 `0x1F16` (65-byte payload → long packet) | `08 AA DD 06 00 00 00 01 1F 16 01 00 41 01 4D 79 20 56 6F 69 63 65` + 490 × `00` (512 B) |
| Voice profile `0x1F05` (374-byte payload) | `08 AA DD 06 00 00 00 01 1F 05 01 01 76 00 <txMask> <372-byte ModAlgBelT>` + pad (512 B) |
| Heartbeat **reply** (illustrative; src 1, dst 6, type 3 assumed) | `08 BB DD 01 06 00 00 01 60 00 03 00 1E` + 30-byte body (§5.2) + pad |
| SET ack (illustrative) | `08 BB DD 01 06 00 00 01 10 03 02 00 01 00` + pad (body `00` = `SetResult.SUCCESS`) |

### 3.4 Differences from the legacy `AA DD` framing in `src/lib/protocol/codec.ts`

| Aspect | Legacy (6118/6301/6302) | 6303 |
|---|---|---|
| Byte 0 | `AA`/`BB` (acts as undeclared report ID) | `08` report ID, then `AA DD`/`BB DD` |
| Addressing | `dst` 0x40/0x41/0x42, `src` 0x80/0x81/0x82 | source 6 + target 0 in the envelope; the unit (TX1–4 = 1–4, RX = 6–9, hot shoe = 10, 0 = this RX) is a **payload field** |
| Command ID | 8-bit | **16-bit BE** + 1-byte frame type |
| Length | BE16 of the single payload | frame count BE16 + per-frame BE16 length |
| Payload endianness | mostly single bytes | **little-endian** multi-byte fields (f32, i16, i32) |
| Packet size | always 64 | 64 or 512 (≥ 512 unpadded) |
| Checksum | none (iOS optional XOR) | none (envelope supports XOR/CRC, disabled) |
| Notifications | none | `NOTIFY` frame type exists; BT events (`0x0029`, `0x002A`, `0x0031`, `0x0032`, `0x0036`) are device-initiated reports **[I]** |

The 6201 (MELO P1) profile of the same envelope differs only in having no report ID, XOR checksum and start/end
frames (`AA DD 06 00 04 00 01 60 00 01 00 00 15` for its heartbeat, unpadded) — a shared "Moma" codec can serve both.

## 4. Session

1. **No handshake / auth.** First command may be the heartbeat. **[V]**
2. On entering the device page (`HLDeviceVolTrack6303Activity.onStart`): start the heartbeat looper (1500 ms,
   `BaseViewModel6303.heartLooper = EventLooper(1500L)`, `startHeartLoop(getHeartTime()=1500)`), and check upgrade
   info. When the first heartbeat arrives: `0x600A` device info for the current RX
   (`rxIndexToDeviceId(currentRxDeviceId)`), then `0x600A` for every online unit + hot shoe
   (`VersionUtilKt.snProbeDeviceIds`), then `0x6012` firmware versions for the current system (`deviceMode`)
   2 s later with a 500 ms retry (`HLDeviceVolTrack6303ViewModel`). **[V]**
3. Page loopers (all `EventLooper`, started/paused with the page):
   | Looper | Interval | Command | Where |
   |---|---|---|---|
   | heartbeat | 1500 ms (iOS 1.5 s) | `0x6000` | `BaseViewModel6303.heartLooper`; I @0x1004b6378 |
   | voice-profile page heartbeat | 1500 ms | `0x1F15` [0] → 6-byte status | `BaseViewModel6303.cantoHeartLooper` (runs instead of `0x6000` while the voice tab is shown, `HLDeviceVolTrack6303Activity` tab switch) |
   | voice-profile edit heartbeat | 2000 ms | `0x1F19` [0] | `cantoSetPageHeartLooper` |
   | BT earphone status | 5000 ms, only when `!is4t4r` | `0x0039` | `EquipmentViewModel.btStatusHeartLooper` |
   | wireless-monitor page | 1000 ms | `0x0039` | `WirelessMonitoringViewModel$btStatusHeartLooper` `EventLooper(1000L)` |
4. **Refresh flag:** heartbeat byte 28 `isRefreshCanto == 1` → app sends `0x6015` (`setBelAppUpdate`) and reloads
   profiles (`EquipmentViewModel.handleNotification`, `CantoViewModel` line ~411). **[V]**
5. **Correlation:** by 16-bit command ID only (no sequence). Requests that address a unit echo the unit in the reply
   payload's first byte (noise/mute/sound-mode/gain replies start with `deviceId`; `0x1F04` with `txPosition`). The
   app drops stale `0x1F04` replies whose `txPosition` differs from the one requested (`CantoViewModel` line ~136).
6. **Notifications:** Bluetooth inquiry results, connect/disconnect events and AVRCP volume reports arrive unsolicited
   while Wireless Monitoring is active (handled in `WirelessMonitoringViewModel.handleNotification`) **[I]**.
7. **Disconnect detection:** USB detach; the page also re-checks the attached PID on `onStart` and goes home if no
   6303 PID is present (`HLDeviceVolTrack6303Activity.reconnectIfNeed`).

## 5. Command catalogue

Payload notation: `u8`, `i16`/`i32`/`f32` little-endian; `[a, b]` = bytes in order. "ack" = 1-byte
`SetResult` (0 = success, 1 = fail; decoders test `payload[0] == SUCCESS`). Every request goes to target 0. iOS
names from `HL6303CommandType` (raw values read from the table @0x100c1a318). Class names are under
`protocol/core/sound/command/device6303/`; IDs from `protocol/core/sound/command/type/Command6303.java`.

### 5.7 Firmware update (documented only — **destructive, do not implement**)

`FirmwareUpgrade6303ViewModel` / `HotShopUpgrade6303ViewModel`: `0x4005` OTA_SEND_TYPE `[devType, system, hasHotShoe]`
→ `0x4000` TRAN_START `{size i32, packageSize i32, crc i32}` → `0x4003` packets (512-byte frames, `wMaxPacketSize−17`
data bytes) → `0x4002` relocation → `0x4009` notify devices `{rx, rxSlave, rxControl, txState, earState, mic}` →

and `0x400B` startRemodeUpdate. Firmware is fetched from Hollyland's server (`application/httpcommon/entities/Firmware6303Info`).

## 7. Reuse assessment

| Library part | Reuse for 6303 | Work |
|---|---|---|
| `transport.ts` contract | Concept reusable; the "64-byte packet, byte 0 = AA/55" assumption is not | Make packet size variable (64/512); byte 0 = report ID 8 |
| `webhid.ts` | `sendReport(packet[0], packet.subarray(1))` already maps byte 0 → report ID, so `08 AA DD …` goes out as report 8 unchanged; `inputreport` → `[reportId, ...data]` rebuild works too | Remove 64-byte assumptions (`PACKET_SIZE`), add 6303 PIDs to filters, receive capability `'unknown'`→ likely `'yes'` on macOS once the descriptor is confirmed |
| `bridge.ts` / node-hid | byte-transparent | allow 512-byte writes |
| `codec.ts` | Not reusable (different header, 16-bit IDs, multi-frame, LE payloads) | **New `codec-moma.ts`**: encode/decode envelope with optional report ID, frame list, flags, XOR/CRC options (also serves 6201) — ~150 LoC, high confidence |
| `commands.ts` (`Cmd`, `COMMANDS`, `Requests`, parsers) | Pattern reusable (safety classes `read/write/disruptive/destructive/ota/notify` map 1:1) | **New `commands6303.ts`**: ID table (§5), payload builders, heartbeat/device-info/firmware/Bel parsers — ~500 LoC, layouts high confidence |
| `device.ts` (`HollylandDevice`) | Queueing, coalescing, timeouts, destructive-command double opt-in, traffic log, `PreconditionError` reusable in spirit | Correlation by 16-bit cmd (+ unit byte), 1.5 s heartbeat, unit model TX1–4 / RX1–4, primary-role gating, restart-causing commands, unsolicited BT events. Best as a family adapter or a sibling `M3Device` — medium effort |
| `models.ts` | `ProductInfo` rows exist (family null) | Add family `'6303'` and capabilities (4 TX, multi-RX, smart mix, hot shoe, bit depth, sound-out, wireless monitoring, voice profiles, camera 3-gear volume); VID **[?]** |
| `mock.ts` | Simulator pattern reusable | `SimulatedM3` speaking the new codec |
| `src/lib/dsp` | **Directly reusable** for voice profiles: `presets.ts` templates + `CmsisEmulator.setEqBand…/getEqCoefficients()` produce exactly the `numStages` + `coeffs` the app writes into `ModAlgBelT`; Web Audio preview already exists | ~100 LoC to serialize `ModAlgBelT` (decide iOS-clamped vs Android-raw compressor values) |

**Effort / confidence without hardware:** read-only status (heartbeat, device info, versions) + home-page setters +
More Settings: ~2–3 days, **medium-high** confidence (framing and payload layouts are generated code, semantics are
from UI usage). Voice profiles: +1 day, **medium** (bytes certain, firmware tolerance of browser-computed coefficients
unverified). Wireless monitoring and multi-RX: +1–2 days, **medium-low** (event-driven, hard to test blind).
Transport (report-ID 8 declaration and report sizes on macOS/Windows): **must be checked on hardware first**.

### 7.1 First things to verify on an M3

1. HID report descriptor (WebHID `device.collections` or `ioreg -l`): is report ID 8 declared for input and output,
   with which sizes? Interface/endpoint sizes (expect HS 512).
2. VID.
3. Send `08 AA DD 06 00 00 00 01 60 00 01 00 00` + padding as report 8; capture the reply's source/target/type bytes.
4. Whether short (63-byte) writes are accepted when the descriptor declares 511, and vice versa.
5. PID before/after switching to 4-track.
