# LARK A1 family (`6108` / `A6108`, USB PID 1031): feature-report protocol ("ProtocolV2")

Research for the group "a1-6108". Scope: the LARK A1 and its firmware variants (2 Mic & 1 RX, 4 Mic & 1 RX),
as driven by `usbmic/protocolV2`, `usbmic/messenger/UsbMessengerV2`, `usbmic/protocolV2/ProtocolFactoryV2`,
`application/common/manager/UsbHandlerManager` and `usbmic/core/USBHIDService` in Android, and by the
`HL6108*` classes in iOS.

Scope: documentation only. Nothing here was sent to any hardware. No A1 is available for testing.

Citation conventions follow `docs/PROTOCOL.md` and the sibling family docs:
- **A:** Android HollyAudio 3.1.0 jadx sources. Paths are relative to `jadx-out/sources/com/hollyland/`.
  The shared `jadx-out` had been cleaned up, so this research used a fresh jadx 1.5.6 decompile of the same
  `com.hollyland.larkc1.apk` (from `HollyAudio_3.1.0_APKPure.xapk`), in
  `scratchpad/families-a1-6108/jadx-out/`.
- **R:** Android resources (`res/values/strings.xml`, `res/layout/…`). Chinese strings come from `config.zh.apk`.
- **I:** iOS `larkSound` 3.1.0 arm64. The citation gives the selector and `@0x…` address (image base
  0x100000000). The text segment is readable even though one 4 KiB page is marked FairPlay-encrypted
  (`LC_ENCRYPTION_INFO_64` cryptoff 0x253000, cryptsize 0x1000). `objc_msgSend` stubs were resolved to
  selectors with a small stub decoder (`scratchpad/families-a1-6108/tools/stubs.py`).
- **[?]** marks an inference or unverified claim. **[INF]** marks a claim derived by combining sources rather
  than read directly.

## 0. Key findings

1. **The A1 does not use interrupt endpoints for control.** Every A1 command is an HID class
   **SET_REPORT(Feature, ID 5)** control transfer followed immediately by a **GET_REPORT(Feature, ID 5)** that
   returns the reply. Firmware upload switches to Feature report **ID 6** with 160 bytes. Evidence:
   `usbmic/core/USBHIDService.onEventMainThread(USBDataSendEvent)` selects `UsbTransferType.CONTROL` when
   `productId == 1031`, `usb/core/HlUsbManagerImpl.executeControlTransfer` issues
   `controlTransfer(0x21, 9, 0x0305, 0, buf, 64)` and then `controlTransfer(0xA1, 1, 0x0305, 0, buf, 64)`, and
   `application/common/manager/UsbHandlerManager` holds `REPORT_ID_NORMAL = 773 (0x0305)`,
   `REPORT_ID_UPGRADE = 774 (0x0306)`, `USB_PKT_SIZE_6108_NORMAL = 64` and `USB_PKT_SIZE_6108_UPGRADE = 160`.
2. **This is the best candidate for full two-way control on macOS.** Feature reports are control transfers
   (`IOHIDDeviceSetReport` and `IOHIDDeviceGetReport` with `kIOHIDReportTypeFeature`). They do not go through
   the input-report path that drops the A2's undeclared report ID 0xBB. In WebHID the mapping is
   `device.sendFeatureReport(5, data63)` followed by `device.receiveFeatureReport(5)`. The one condition
   **[?]**: Chrome sizes the GET_REPORT buffer from the descriptor's declared feature-report size, so the A1's
   report descriptor must declare Feature report 5. The firmware answers GET_REPORT(Feature, 5) with 64 bytes
   on Android, which makes that very likely, but nobody has dumped the descriptor.
3. **The framing is "legacy-like" but not compatible.** The request is
   `05 03 AA DD <cmd> <lenHi> <lenLo> <payload…> EF 00…` (64 bytes including the report ID). The reply is read
   with the command at offset 4 and the payload at offset 7. There is no RX/TX address byte, because the target
   unit travels in the payload, and the frame ends with an `0xEF` end marker instead of nothing or an XOR. Set
   replies use **`body[0] == 0` = success** (Android; iOS accepts anything but `0xFF`, §3.2), the opposite of the A2/M2 rule. Command numbers are a different
   table: `0x1F` is the heartbeat, `0x05` is reverb rather than volume, and so on. Source:
   `application/common/protocol/ProtocolV2.getData/parse`.
4. **Android and iOS agree on the command layer.** iOS talks to the A1 over iAP2/EA with the "short" builder
   `AA DD <cmd> <lenHi> <lenLo> <payload> <XOR>` (`+[NSData(HL6902Data) headerWithCommand:payload:]
   @0x10027a9ac`). It uses the same command IDs (`-[HL6108EventMapper eventTypeForCommand:] @0x10001e120`),
   the same payload encodings (`-[HL6108DefaultPayloadCodec payloadForAction:deviceType:] @0x1002e0760`) and the
   same 23-byte heartbeat layout (`-[HLHeartEntity initA1HeartInfo:] @0x1001fa798`). That gives two independent
   confirmations of IDs, payloads and the heartbeat.
5. **There are features the A2 lacks:** a 3-preset EQ, a 3-step reverb, **per-mic mute from the app**,
   4-mic operation (2T1R or 4T1R firmware), "Mode setting" (Normal / Performance signal mode) and a hidden,
   cloud-driven "performance mode" flag. Missing compared with the A2: voice presets, smart battery, factory
   reset (hidden), and phone-speaker passthrough (hidden).

## 2. Transport

### 2.1 USB (Android, the reference for a browser)

* **Discovery.** Same as other USB families: VID 0x3547 and the PID is read for routing
  (A `usbmic/core/USBHIDService.onServiceCreate$lambda$1`, `isSupportedUsbDevice`). Android still claims "the
  first HID-class interface with an interrupt endpoint" (A `usb/core/HlUsbManagerImpl.findSuitableInterface`)
  and starts the interrupt-IN read loop (`startDataReceiveLoop`), but A1 commands never use those endpoints.
* **Control path** (A `USBHIDService.onEventMainThread(USBDataSendEvent)` → `HlUsbManagerImpl.executeControlTransfer`):

  | Step | bmRequestType | bRequest | wValue | wIndex | wLength | Data |
  |---|---|---|---|---|---|---|
  | write | `0x21` (class, interface, OUT) | `0x09` SET_REPORT | `0x0305` = Feature, ID 5 (`0x0306` during OTA) | `0` | 64 (160 during OTA) | the frame, byte 0 = report ID |
  | read  | `0xA1` (class, interface, IN) | `0x01` GET_REPORT | same as write | `0` | same as write | the reply, byte 0 = report ID [INF] |

  * The `UsbCommandInfo(…, 488, null)` constructor mask leaves `needResponse` at its default `true`,
    `controlRequestRead = 1` and `controlRequestWrite = 9`
    (A `protocol/core/parser/UsbCommandInfo.<init>(…, int i5, …)`).
  * wIndex is hard-coded to **0**, so the A1's HID interface is interface 0 [INF].
  * Timeouts: **write 3000 ms, read 1000 ms** for PID 1031 (`new CommandExecutionConfig(3000L, 1000L, …)` in
    `USBHIDService.onEventMainThread`). There is no transfer-level retry. On failure the command is marked
    FAILED and dropped (`executeControlTransfer`).
  * One command is in flight at a time (`usb/core/queue/UsbCommandQueue` + `startCommandProcessingLoop`). Raw
    `USBDataSendEvent`s get random names, so there is no de-duplication.
  * Mode switch: `UsbHandlerManager.updateTransportConfig(isTransferring)` toggles `controlTransSize` 64 ↔ 160
    and `reportId` 0x0305 ↔ 0x0306 globally. `ModeSwitchActivity` / `VersionInfoActivity` call it around OTA.
* **Report sizes** [INF]: Feature 5 = 1 ID byte + 63 data bytes. Feature 6 = 1 + 159. These come from
  wLength. The descriptor has not been captured.
* **No unsolicited traffic.** Every reply is pulled by GET_REPORT. Nothing in the V2 code expects
  interrupt-IN data. `USBDataReceiveEvent.updateUSBData` would route such data through `ProtocolFactoryV2`, but
  no device-initiated command exists.

### 2.2 iOS

iAP2 External Accessory stream, max 64 bytes per write and a 20 ms sleep before each `AA DD` write
(`-[EADSessionManager writeSimpleData] @0x1001239cc`, see `ios-protocol.md` §1.2). Writes go through
`-[HL6108Transport sendAction:] @0x1002e19c4` → `payloadForAction:deviceType:` → `headerWithCommand:payload:` →
`+[HLMessageUtils sendMsg:]`. A browser cannot reach this path, but it confirms the command layer.

### 2.3 Browser path

| API | Fit | Platforms | Notes |
|---|---|---|---|
| **WebHID** `sendFeatureReport(5, data)` + `receiveFeatureReport(5)` | **Primary** | Chrome/Edge desktop: macOS, Windows, Linux, ChromeOS | Exactly Android's control-transfer pair. **macOS: expected to work in both directions** (feature reports, not interrupt IN). Conditional on Feature report 5 being declared **[?]**. Chromium's macOS backend sizes the GET_REPORT buffer from `max_feature_report_size`, and Windows `HidD_GetFeature` also needs a declared report. Linux hidraw (`HIDIOCSFEATURE/HIDIOCGFEATURE`) does not check. |
| WebUSB `controlTransferOut/In` | No | – | The requests target a HID-class interface, which Chrome protects and will not let a page claim. |
| Web Bluetooth | No | – | The A1 has no BLE path in either app. |
| Local bridge (`scripts/bridge.ts`, node-usb) | Fallback | macOS/Windows/Linux, run as root | Would need a new channel doing `controlTransfer(0x21, 9, 0x0305, 0, buf)` / `controlTransfer(0xA1, 1, 0x0305, 0, 64)` instead of interrupt I/O. Only needed if the descriptor turns out not to declare Feature 5. |
| Android Chrome | No | – | No WebHID. WebUSB cannot claim HID. |

WebHID details to handle **[?]**:
* `sendFeatureReport(5, data)`: `data` is the 63 bytes after the report ID (`frame.subarray(1, 64)`).
* `receiveFeatureReport(5)` returns a `DataView`. In Chromium it normally **includes the report ID as byte 0**,
  unlike `inputreport` events, but this varies by backend. A decoder should accept both: if
  `view.byteLength === 64 && view.getUint8(0) === 5`, drop byte 0.
* GET_REPORT can return the previous reply if the firmware is slow. Android does not delay, so this is probably
  fine, but the decoder should check that the echoed command (offset 4) matches the request and retry the GET
  once if it does not.

## 3. Framing

### 3.1 Request on Feature report 5 (A `application/common/protocol/ProtocolV2.getData`)

```java
byte[] b = new byte[UsbHandlerManager.getControlTransSize()];   // 64 (160 while OTA mode is on)
b[0]=0x05; b[1]=0x03; b[2]=0xAA; b[3]=0xDD; b[4]=getCmd();
if (payload.length != 0) arraycopy(NumberUtil.intToByte2(payload.length), 0, b, 5, 2);   // big-endian
if (payload.length != 0) arraycopy(payload, 0, b, 7, payload.length);
b[payload.length + 7] = 0xEF;
```

| Offset | Size | Value |
|---|---|---|
| 0 | 1 | `0x05`: report ID, matching wValue low byte |
| 1 | 1 | `0x03`, constant for every command. Meaning unknown; it is not a length. |
| 2–3 | 2 | `AA DD` |
| 4 | 1 | command ID (§5) |
| 5–6 | 2 | payload length, **big-endian** (`NumberUtil.intToByte2`); `00 00` when empty |
| 7…6+n | n | payload |
| 7+n | 1 | **`0xEF` end marker** |
| 8+n…63 | – | `0x00` |

* There is no checksum. `ProtocolV2.crcCalculate` (XOR of all bytes) exists but has no caller.
* There is no sequence number and no unit address byte.
* The maximum payload is 56 bytes (64 − 7 − 1). No A1 command needs more than 2.
* **WebHID:** `sendFeatureReport(0x05, frame.subarray(1, 64))`.

### 3.2 Reply from GET_REPORT(Feature 5) (A `usbmic/events/USBDataReceiveEvent.updateUSBData`, `ProtocolV2.parse`)

| Offset | Value | Notes |
|---|---|---|
| 0 | `0x05` report ID [INF] | not checked |
| 1 | unknown (request has `0x03`) | not checked |
| 2–3 | `BB DD` [INF] | not checked by Android. iOS EA replies start `BB DD <cmd> <len16> <payload>` (`-[EADSessionManager dealWithCurrentData] @0x100124228` strips 2 bytes, then `-[HL6108PacketParser parseMessageFromData:] @0x1002e06e0` reads the command from byte 0), which lines up with Android's command at offset 4. |
| 4 | **command ID (echo)** | `this.command = data[4]` → `ProtocolFactoryV2.createProtocol(cmd)` |
| 5–6 | payload length | Android computes `data[5]*16 + data[6]` (same ×16 bug as M2; harmless because `data[5]` is always 0). Parse fails if the length is 0 or greater than `data.length − 7`. |
| 7… | payload ("body" below) | `receiveData(payload)` |

Exceptions, all report-6 OTA replies (`ProtocolV2.parse`): for commands `0x1A/0x1B/0x1C` the payload is
`[data[5]]`, and for `0x1D/0x1E` it is `[data[9]]`. In those replies the 4-byte LE offset is echoed at 5–8 [INF].

**Set acknowledgements:** every `ProSet*` / OTA class decodes `setStatus = (body[0] == 0)`. Note that
`DeviceConnectVariable.CmdSetResult` defines SUCCESS(0) and FAILURE(1). **This is inverted relative to the
A2/M2 rule (`body[0] == 1`).**

**iOS decodes the same ack differently [V] (added 2026-11-05, Phase 0/1 review):** success = `body[0] != 0xFF`
(I `-[HL6108DeviceInfoSync handleEvent:]` @0x100203d98, event-type-3 branch @0x1002040b0: `subdataWithRange:(3, 1)`
of the `cmd len16 payload` message = body[0] @0x1002040c8, `coverDecimalismData:`, `cmp x0, #0xff; cset w24, ne`
@0x1002040e8, then `+[HL6108Effect configResultWithCommand:success:]` @0x100204114). Event type 3 covers the set
commands `0x01/0x03/0x05/0x07/0x13/0x16/0x21/0x23/0x27/0x3F` (`-[HL6108EventMapper eventTypeForCommand:]`
@0x10001e120, jump table @0x100c160c8). The apps agree only that `0x00` is success; a reply of `0x01` is a failure on
Android and a success on iOS. The library keeps Android's rule (`families/6108/status.ts parseA1Ack`, which also
returns `iosOk`), and the traffic log flags a failure iOS would accept. Which reading the firmware follows is a
hardware-check item (§ hardware check, toggle the LED).

### 3.3 OTA / DFU on Feature report 6, 160 bytes (A `usbmic/messenger/UsbMessengerV2.sendRxUpgrade/sendTxUpgrade/enterDfu/sendOTAPkg/verifyCrc`)

| Offset | Value |
|---|---|
| 0 | `0x06` (report ID) |
| 1 | N = number of bytes from offset 3 to the last meaningful byte: 3 for bare commands, 15 for DFU-enter, `128 + 7 = 135` for a data packet |
| 2–3 | `00 00` |
| 4 | service: `0` = `APP_SERVICE_HANDSHAKE` (0x1A/0x1B), `2` = `APP_SERVICE_OTA` (0x1C/0x1D/0x1E) |
| 5 | command: `0x1A` RX upgrade, `0x1B` TX upgrade, `0x1C` enter DFU, `0x1D` data, `0x1E` verify |
| 6… | 0x1C: `firmwareType u32 LE, firmwareVersion u32 LE, firmwareSize u32 LE` (the app sends 0, 0, file length). 0x1D: `offset u32 LE` + 128 data bytes. |
| rest | `0xCD` padding to 160 |

Data chunks are **128 bytes** (`DeviceDataManager.USB_DATA_PKT_SIZE_6108 = 128`, `get6108PkgCount`,
`getDataWithIndex`), and the offset advances by 128 per acknowledged packet (`ModeSwitchActivity.onResTransmitData`).

### 3.4 iOS EA framing (reference only)

`+[NSData(HL6902Data) headerWithCommand:payload:] @0x10027a9ac`: `AA DD <cmd> <lenHi> <lenLo> <payload> <XOR>`,
where the XOR covers every preceding byte starting at `0xAA` (`getOrData:`). The bare variant
`headerWithCommand: @0x10027ab54` is `AA DD <cmd> 00 00 <XOR>`. The A2/M2 builder differs: it has a type byte
`0x40|t` and goes through `headerWithCommand:payload:andType:`. **Do not use the XOR form on HID**: Android puts
`0xEF` after the payload instead of an XOR.

### 3.5 Differences from the legacy `AA DD` framing in `src/lib/protocol/codec.ts`

| | Legacy (A2/M2/M2S) | A1 (ProtocolV2) |
|---|---|---|
| USB transfer | interrupt OUT, async interrupt IN | SET_REPORT + GET_REPORT, Feature ID 5, synchronous |
| Byte 0 on the wire | `AA` (acts as an undeclared report ID) | `05` (Feature report ID) |
| Header | `AA DD cmd dst lenHi lenLo` (6 bytes) | `05 03 AA DD cmd lenHi lenLo` (7 bytes) |
| Unit address | `dst` 0x40/0x41/0x42, reply `src` 0x80/0x81/0x82 | none. The unit goes in the payload (0..4, or a 0-based TX index), and version/SN replies return it in `body[0]`. |
| Trailer | none | `0xEF` |
| Set ack | `body[0] == 1` = OK | `body[0] == 0` = OK |
| Units | RX + TX1/TX2 | RX + TX1..TX4 |
| Heartbeat | `0x10`, 17 bytes | `0x1F`, 17, 22 or 23 bytes (§4.2) |
| Correlation | by echoed command + `src` | implicit (request/response pair), plus echoed command |

## 4. Session

### 4.1 Handshake and start-up

* **There is no handshake or authentication.** `UsbMessengerV2.APP_SERVICE_HANDSHAKE = 0` is only the
  service byte of the OTA frames.
* **Android start-up** (A `larkc1/HLDevice6302Activity.onStart` → `getDeviceVersion()`):
  1. `0x12 [00]` serial of the RX, `0x0D [00]` version of the RX, `0x30` RX MAC. TX1..TX4 units are queried
     only if already known to be online, which is false on first entry.
  2. The legacy getters (`getNoiseLevel/getVoiceLevel/getSpeaker/getVoiceLock`) are skipped for the 6108
     (`if (!this.is6108Device)`).
  3. The heartbeat `0x1F` starts **1000 ms after** the audio-record permission callback
     (`onPermissionGranted` → `mHandler.postDelayed(mRunnable, 1000)`). It then repeats **every 1000 ms**
     (`HLDevice6302Activity$mRunnable$1.run`) and stops in `onStop`. The settings, signal-mode and mode-switch
     screens run their own 1 s `0x1F` loops (`SettingActivity.onStart`, `SignalModeActivity.onCreate`,
     `ModeSwitchActivity.startSendHeart`).
  4. When a TX goes from offline to online in a heartbeat, the app waits 1 s and then sends `0x0D [n]`,
     `0x12 [n]` and `0x31 [n−1]` (`onResHeartInfoV2` coroutines `C11741`, `C11752`, `AnonymousClass3/4`).
  5. After each MAC reply, `HLDevice6302ViewModel.handleDeviceMac` reports the MAC to the cloud and fetches the
     SN bound to it (`HttpRepository.reportDeviceMac`, `getDeviceMacBindInfo`). It then sends `0x46` (get
     performance flag). `handlePerformanceMode` fetches the cloud config `EnhancedModeSwitch`
     (`HttpRepository.getPerformanceModeConfig`). If the value differs from the device, it **silently sends
     `0x45 [v]`**, at most once per view model (`hasSetPerformanceMode`).
* **iOS start-up** (I `+[HL6108Messenger getDeviceInitialInfo] @0x1002e0dd8`): `0x02` (get channel mode) at
  t = 0. Then `dispatch_after` blocks at 1.0 / 1.5 / 2.0 / 2.5 / 3.5 s send `0x08` (get EQ), `0x0D [00]`,
  `0x12 [00]`, `0x30` (RX MAC; the iOS selector is misleadingly named `sendGetDeviceTXMacWithType`) and
  `0x46`. The block-to-time mapping follows code order [INF]. iOS then mirrors the cloud `EnhancedModeSwitch`
  logic (`-[HL6108DeviceInfoSync requestEnhancedModeStatus:] @0x100205f58`, `checkEnhanceStatus:
  @0x100204e1c` → `+[HL6108Messenger sendSetPerformanceEnabled:] @0x1002e165c`).
* **iOS heartbeat:** `-[HLDeviceController sendHeartInfo] @0x1002c4998` sends `AA DD 1F 00 00 68` for
  `protocolType 2` on a **3.0 s** `NSTimer` (@0x1002c4230). It is skipped while `curUpgrateType == 3`.
* **iOS read-back after each set** (I `-[HL6108DeviceInfoSync queryCommandForSetCommand:] @0x100204d88`):
  `0x01 → 0x02`, `0x07 → 0x08`, `0x3F → 0x46`, and `0x03/0x05/0x13/0x16/0x21/0x23/0x27 → 0x1F`. Note that
  iOS pairs set-signal-mode (`0x3F`) with get-performance (`0x46`), whereas Android pairs `0x3F` with `0x40`.
  This is an unresolved discrepancy **[?]**.

### 4.2 Heartbeat `0x1F` reply body

From A `usbmic/protocolV2/ProGetHearInfo.receiveData` → `usbmic/data/HeartInfoBean`. Each field is read only if
`body.length` covers it. Cross-checked byte for byte against I `-[HLHeartEntity initA1HeartInfo:]
@0x1001fa798`, which reads the same fields at buffer offsets 3+i, where buffer = `cmd len16 body`.

iOS branches on the LEN field (`x21`, @0x1001fac5c–0x1001facbc), which shows that **three body lengths exist**:
* LEN < 17: stop after body[15] (no signal-mode byte).
* LEN == 17: 2-mic layout. Stop after body[16].
* LEN == 23: body[16] is signal mode and TX3/TX4 are at body[17..22]. This is the layout Android assumes.
* Any other LEN > 17 (for example 22): TX3/TX4 are read from **body[16..21]**, so there is no signal-mode byte
  and a 4-mic firmware predates signal mode. Android does not handle this case and would misread TX3/TX4 on
  such firmware **[?]**.

A web implementation should follow iOS: branch on LEN.

| body[i] | Field | Decoding / UI |
|---|---|---|
| 0 | tx1Online | `== 1` |
| 1 | tx2Online | `== 1` |
| 2 | tx1Battery | 0–100 %. The UI hides the battery if it is 0 or the mic is offline. |
| 3 | tx2Battery | % |

### 4.3 Timeouts, errors and notifications

* Android: SET_REPORT 3000 ms, GET_REPORT 1000 ms, no retry, one command at a time. A missing or empty reply
  leaves the UI in its optimistic state. `UsbMessengerV2.onEvent` does not check `isValid`, so an empty set
  reply shows the "Setup failed" toast.
* The OTA and mode-switch flows retry each step up to 5 times (`sendDeviceCount < 5`), with a 90 s upgrade
  timeout (`ModeSwitchActivity.startUpgradeTimeoutTimer`) and a 3 s `0x2D` poll (`startAskTxOTAResult`).
* There are no notifications. Mute changes made with the mic button, connection changes and battery all
  arrive only through the polled heartbeat.

**Destructive or disruptive commands:** everything from `0x0C` down in the table. The **wireless mode switch**
(`ModeSwitchActivity`) is a full re-flash of RX and mics with the other mode's firmware: `0x2C` → `0x1A`/`0x1B` →
`0x1C` → `0x1D`… → `0x1E` → `0x2D` poll → `0x3C`/`0x3D`/`0x3E`. The iOS copy warns "Mode switch takes about 5 minutes. Please keep the
device connected…" (`Localizable.strings` `无线切换需要5分钟左右时间…`), and the mics have to be re-paired
afterwards (Android `ModeSwitchActivity.sendRxIntoPair` / `moreMicExist`). **Do not implement this without hardware.** The A1 has no factory-reset command, no
remove-pairing command, and no command to set gain per TX.

**App-side only:** VU meters (`blemic/utils/AudioRecordUtils`, the same as M2S), the SN-by-MAC cloud mapping,
the cloud feature flags (`ModeSwitch`, `WirelessSwitch`, `EnhancedModeSwitch`), firmware download and
analytics (`HAnalyticsReportUtils`).
