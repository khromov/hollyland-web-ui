### Apple float libm emulation

Apple's float `powf`, `sinf`, `cosf`, `expf`, `logf` and `log10f` are not correctly rounded: each is a short table-driven routine that evaluates in double precision with fused multiply-adds and rounds once at the end, and about 0.6–1.3% of its results are one ulp away from `Math.fround(Math.fn(x))`. Where the DSP calls one per sample (the airfresh soft clipper, the LUFS gain of the offline render) such a one-ulp step is enough to decorrelate the float32 rounding noise of the high-Q, low-frequency EQ sections that follow, so earlier versions of the port, which used correctly rounded libm, missed the targets there (up to 1.7e-5 on the exciter, 74 dB SNR offline). The port now reproduces each routine instruction for instruction from the disassembly of libsystem_m (same tables, same polynomial, same FMA order, exact `fma64`), so its double intermediate and float result are the library's.

Check against this Mac's libm: **14,000,000 calls, every result bit-identical** to the emulation. Tables: the committed `src/lib/dsp/applelibm-data.ts` is identical to what `.dsp-native/bin/libm-tables` reads out of this Mac's libsystem_m.

## How it is measured

- **Native reference:** `cmsis_api_ios` from the installed larkSound.app (sha256 `5cc3283858bee6e35e8eaed9b526a7b1543c00d77c283ae338e7d877e1398389`), retagged as a macOS arm64 dylib and ad-hoc signed by `npm run dsp:prepare`, called through `.dsp-native/bin/cmsis-runner` (`tools/dsp-harness/native/runner.c`). The library is never committed; the prepare script regenerates it from the user's install.
- **CR libm diagnostic:** the same runner with `--libm cr` rewrites the library's `__got` slots for `powf sinf cosf tanf expf logf log10f` to wrappers that evaluate the double function and round once (the vendor code is otherwise untouched), and the port runs with `setLibm('cr')`, which uses `Math.fround(Math.fn(x))`.
- **Port under test:** `VoiceProcessor` / `CmsisEmulator` from `src/lib/dsp`, run in Node by `tools/dsp-harness/compare.ts`.
- **Same calls on both sides.** Each scenario is a list of API calls (init, default_configs, setters, process) interpreted by both sides. One runner process (one library load) and one `VoiceProcessor` per scenario; every signal starts from `cmsis_init` or a preset (which begins with `cmsis_default_configs`).
- **Presets.** Native side: the runner reads the app's own template JSON and applies it with a C re-implementation of the iOS app's mapping (clamps, `lroundf` of attack/release, exciter type 2 disables, `default_configs` first). TS side: `VoiceProcessor.configure()` with `PRESET_TEMPLATES`. The two template sources are cross-checked below.
- **De-esser range on iOS.** `cmsis_set_esser` in the iOS build never stores its range argument, and `cmsis_init` leaves that field as uninitialised heap memory. The runner reports the value it finds after `cmsis_init` (a note appears below if it is ever non-zero) and pins it to 0 for iOS-behaviour scenarios, which is what the port assumes. The `full-android` scenarios write the template range (−15 dB) into the field instead, which is what the Android library does.
- **Frames.** `cmsis_process_frame` takes 240-sample frames; both sides process whole frames on the same grid, and the runner copies each input frame first because the native EQ runs in place on its input. Both native outputs (A and B) are checked to be identical.
- **Alignment.** Nothing is shifted before measuring. For every row the error energy at lag 0 is compared against lags ±1 and ±240 (one frame), and against every lag within ±480 around the worst error when SNR < 80 dB. The lag column shows the best one; a non-zero lag would be noted and still counted as a failure at lag 0.
- **Offline render.** `cmsis_process_wav` reads a float32 WAV written by the harness and writes stereo float32; the port's `processWavSamples` is compared on both channels (interleaved). Its WAV writer reuses the first call's length for later calls in the same process, so each signal gets its own runner process there.
- **LUFS stage alone.** The runner calls the library's own `lufs_init` and `dsp_integrated_loudness` per sample; this stage is not part of the real-time path.

The worklet regroups Web Audio's 128-sample render quanta into the library's 240-sample frames (`src/lib/dsp/stream.ts`), which delays every channel by **224 samples (4.67 ms at 48 kHz)**: the smallest delay at which the output never runs dry, 240 − gcd(128, 240). Each channel output must start with exactly that many zero samples and then match, bit for bit, the same TS code run in Node on 240-sample frames, and the app's native library run on the same input (one fresh library load per channel).

- 2026-11-05, step 1: First harness run. Two harness bugs, fixed in the harness, not by loosening anything: (1) the full-chain scenarios applied presets without `cmsis_init`, so `cmsis_process_frame` returned −3 and the native output was silent; they now call `init` first, as the app does. (2) `cmsis_process_wav` reuses the first call's output length for every later call in the same process (static state in its WAV writer), which made later offline renders longer than their input; offline scenarios now use one runner process per signal.
- 2026-11-05, step 2: Baseline with the harness fixed: EQ coefficients (8 presets) 0 ulp; EQ, compressor, pipe, full chain (8 presets, iOS behaviour) and the live-switch sequences 100% bit-identical. Misses: `dist:air-1` max 1.74e-5 (target 1e-5) and `offline:rich-full` SNR 74.3 dB (target 80 dB). De-esser (range −15) max 5.4e-7, airfresh wet 0.5 max 8.7e-6, LUFS max 4.8e-7, GRU max 7.1e-15 (99.999% bit-exact).
- 2026-11-05, step 3: Added the `--libm cr` runner mode (the library's float libm imports rebound to correctly rounded wrappers) to separate libm rounding from porting errors. Against it, airfresh, de-esser, LUFS, offline render and the 4000-band EQ coefficient sweep become bit-identical; only `dist:gru-*` still differed (max 7.1e-15), so that one was a port issue.
- 2026-11-05, step 4: Port fix (`src/lib/dsp/f32.ts`, `exciter.ts`): the GRU fed V8's `Math.tanh` into its double FMA. V8's tanh is one double ulp off on about 30% of inputs (measured against macOS `tanh`), and in decaying GRU tails (input 0, state around 1e-7) the FMA result sits exactly on a float midpoint that the tanh correction term decides. New `tanh64` uses the odd Taylor series below 2^-11, which matched macOS `tanh` on all 2·10^6 tested inputs there. `dist:gru-0.5` / `dist:gru-1`: 99.999% → 100% bit-identical against both libm modes.
- 2026-11-05, step 5: Port fix (`src/lib/dsp/pipeline.ts`): `CmsisEmulator.init()` no longer clears the distortion init flag. Natively it is a `static int` just past the context that `cmsis_init`/`cmsis_deinit` zero, so `distInit` runs once per library load. No row changed (valid call sequences cannot observe it); covered by a unit test.
- 2026-11-05, step 6: Added the random-configuration (`fuzz:*`) scenarios, the libm statistics and the CR-libm columns to the report. Fuzz configurations: bit-identical against CR libm, ≥ 99.0% bit-exact and max 1.1e-7 against Apple libm.
- 2026-11-05 02:10 UTC: Final state after the fixes above: every row bit-identical against the CR-libm library; dist:air-1 and offline:rich-full miss their targets against Apple's libm only (run: 727/732 target rows met; 780/780 rows bit-identical against CR libm)
- 2026-11-05 02:45 UTC: Round 2: the port now emulates Apple's arm64 float libm (powf, expf, logf, log10f, sinf, cosf) instruction for instruction from the libsystem_m disassembly (src/lib/dsp/applelibm.ts).
